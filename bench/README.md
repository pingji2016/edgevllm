# 回归基准（bench）

把 `docs/ubuntu-ai-box` 里的关键结论变成**可执行、可验证**的检查。
换机器、升级依赖、改配置之后，跑一遍就知道结论还成不成立。

## 快速开始

```bash
cd ~/apps/edgevllm/bench

python run.py                  # 快检查（纯数学 + 带宽 + 文档索引），约 1 分钟
python run.py --include-slow    # 加上需要加载模型的检查，约 4 分钟
python run.py --list            # 看看有哪些检查
python run.py --only rag_r1     # 只跑某一项
```

退出码：全过 `0`，有失败 `1`（可直接接 CI）。

## 检查清单

| 检查 | 类型 | 验证什么 | 期望 |
| --- | --- | --- | --- |
| `kv_bytes_per_token` | 纯数学 | KV 每 token 字节数 | 114,688 B |
| `decode_roofline_1p7b` | 纯数学 | 带宽 ÷ 权重 | 131.8 tok/s |
| `spec_break_even` | 纯数学 | 投机加速比公式 | 1.00× |
| `concurrency_32k` | 纯数学 | 32K 上下文的并发上限 | 2.2 路 |
| `docs_indexed` | 纯文本 | 每篇 md 都在 README 里 | 100% |
| `gpu_bandwidth` | GPU | 显存拷贝带宽 | ≥340 GB/s |
| `rag_r1` | GPU+模型 | 12 题检索命中 | ≥67% |
| `json_compliance` | GPU+模型 | 10 题结构化输出 | ≥90% |
| `needle_8k` | GPU+模型 | 8K 上下文检索 | ≥75% |

## 为什么是这些

它们分别对应文档里**最容易被环境破坏**的四类结论：

1. **物理上限**（带宽、KV、并发、投机）——纯公式，任何机器都能验；
2. **显存带宽**——换卡/换驱动最先变的就是它；
3. **检索质量**——嵌入模型或索引一变就崩，是最脆的一环；
4. **模型行为**（JSON、长上下文）——量化/引擎/模板改动会悄悄改变它。

## 期望值在哪改

全部在 `manifest.json`。改约定不用碰代码：

```json
"rag_r1": { "min": 0.67, "unit": "R@1", "why": "基线 75%，留 8pp 容差" }
```

- `expect` + `tol`：数值型，判断 `|实测−期望| ≤ tol`
- `min`：下限型，判断 `实测 ≥ min`

每一项都带 `why`，说明这个数字是怎么来的。

## 设计约定

1. **快检查不加载模型**：默认 1 分钟内跑完，适合每次改动后跑；
2. **慢检查单独开关**：`--include-slow`，适合发布前跑；
3. **失败要能定位**：每项输出实测值、期望值和一句细节（如 `9/12 题命中`）；
4. **容差要诚实**：模型类检查给足噪声空间（如 R@1 基线 75%，下限设 67%）。

## 已知局限

- 慢检查需要：`~/models/bge-m3`、`~/models/.rr_done`（reranker）、`rag/chunks.jsonl` + `emb_m3.npy`；
- 跑模型前要停常驻服务：`echo 123456 | sudo -S systemctl stop vlm-server`；
- 这些检查验证的是**结论是否还成立**，不是"跑分"——不要拿它当性能基准。
