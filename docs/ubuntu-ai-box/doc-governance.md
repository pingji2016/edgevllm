# 文档治理：给切片加结构，救不了"主题稀释"

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-26
> 承接 `hybrid-retrieval.md`：R@1 到 75%，剩下 3 题里 1 题完全没召回

上一轮把检索做到 **R@1 75% / R@3 83% / R@5 92%**，剩下的失败被归因为
"20+ 篇 K3 文档主题稀释"。这一轮试**不改内容、只加结构**能不能救：

> **结论：三种结构手段全部无效，其中两种还把结果拉低了。**
> **75% 就是这套检索栈在这个语料上的天花板。**

---

## 1. 六种配置

所有配置都基于同一套 bge-m3 向量 + bge-reranker-base，只改"喂给检索的结构信息"：

| 配置 | 做法 |
| --- | --- |
| **A 扁平** | 1,726 个切片直接检索（基线） |
| **B 标题前缀** | 每个切片前拼 `[文件名] 章节标题` |
| **C 文档路由** | 先用文档摘要选 top-3 文档，只在这些文档内检索 |
| **D B+C** | 标题前缀 + 文档路由 |
| **E 并集（路由）** | 扁平 top-20 ∪ 路由候选 top-20，再重排 |
| **F 并集（标题）** | 扁平 top-20 ∪ 标题前缀 top-20，再重排 |

语料是仓库里的 **77 篇文档**（不只 ubuntu-ai-box 那 27 篇），切片仍是 1,726 个。

---

## 2. 结果

| 配置 | R@1 | R@3 | R@5 |
| --- | ---: | ---: | ---: |
| **A 扁平（基线）** | **75%** | 83% | **92%** |
| B 标题前缀 | 67% | **92%** | 92% |
| C 文档路由（top-3） | 67% | 67% | **67%** |
| D 标题 + 路由 | 67% | 67% | 67% |
| E 并集（扁平∪路由） | 75% | 83% | 92% |
| F 并集（扁平∪标题） | 75% | 83% | 92% |

### 2.1 三种手段各自的失败方式

**B 标题前缀：R@3 涨了 9 pp，R@1 掉了 8 pp。**
前缀让"相关文档"更容易进 top-3，但也稀释了切片本身的相似度，
导致最该排第一的那条被别的文档片段挤下去。

**C 文档路由：直接崩到 67/67/67。**
把候选限制在 top-3 文档里，等于**提前剪枝**——如果正确文档没进 top-3，就永远找不回来。
R@5 也掉到 67%，说明有 4 题被彻底剪掉。

**E/F 并集：理论上"只增候选不会更差"，实测确实没变差，但也没变好。**
这反而说明：**失败不在排序层**。重排器早就看到了正确文档，
问题是正确文档**根本没进嵌入层的候选池**。

## 3. 那 1 题到底错在哪

唯一从头到尾没命中的是：

> "Kokoro 跑在 K3 上的实时率（RTF）是多少？"

它的正确答案在 `tts-kokoro.md`（桌面 RTF 0.014）和 `e2e-and-opt.md`（K3 上 2.08）。
但检索的 top-1 一直是 `README.md`。

更关键的是：**无论扁平 top-20、标题前缀 top-20、还是路由 top-20，
`tts-kokoro.md` 的切片都不在其中。**

> 也就是说，这不是"排序排错了"，是"根本没被找出来"。
> 换重排器、换融合方式、加标题，都动不了这一层。

---

## 4. 为什么摘要路由也没用

理论上"先用文档摘要定位文档"应该能对抗主题稀释。实测反而更差，原因有两个：

1. **摘要本身也相似**：20+ 篇 K3 文档的摘要都在讲 K3、llama.cpp、实测，
   向量空间里挤在一起，top-3 里经常全是同一批；
2. **top-3 太激进**：12 题里有 4 题的正确文档不在 top-3，直接被剪掉。

如果改成 top-10 文档，剪枝风险下降，但候选池又退化成"大部分文档"，
路由就失去了意义——这是个两头堵的结构。

---

## 5. 什么才可能真的有效

按投入产出排序：

| 手段 | 作用层 | 预期 | 成本 |
| --- | --- | ---: | --- |
| **给每篇文档加"关键数字速查表"** | 内容 | 让目标文档更独特 | 人工 |
| **合并 20+ 篇 K3 文档** | 内容 | 消除同主题竞争 | 人工 |
| **查询改写 / 扩展**（"RTF" → "实时率 耗时"） | 查询 | 补词面缺口 | 需小模型 |
| **元数据过滤**（先选主题再检索） | 结构 | 需用户指定主题 | 低 |
| 换更强的嵌入模型 | 嵌入 | 已接近饱和 | 需更大显存 |
| 标题前缀 / 文档路由 / 融合 | 结构 | **实测无效** | — |

> 一句话：**结构手段只能在"候选池里有正确答案"时起作用。
> 候选池里没有，就得改内容或改查询。**

---

## 6. 一个可复用的判据

判断"检索失败"属于哪一层，按这个顺序查：

```
1. 把正确文档手工塞进候选池 → 重排能否排到第一？
   ├─ 能  → 排序层问题（换重排器 / 加特征 / 融合）
   └─ 不能 → 嵌入层问题（改内容 / 查询改写 / 换模型）
2. 正确文档在扁平 top-20 里吗？
   ├─ 在 → 重排问题
   └─ 不在 → 嵌入问题（本轮就是这种）
```

本轮 SoP：正确文档不在任何候选池里 → **嵌入层问题，结构手段无效**。

## 8. 结论

1. **标题前缀**：R@3 +9 pp，R@1 −8 pp，不划算；
2. **文档路由（top-3）**：R@5 从 92% 崩到 67%，**过早剪枝**；
3. **并集**：不变差也不变好 → 证明瓶颈在嵌入层，不在排序层；
4. **75% 是这套栈的天花板**；再往上走只能改内容或改查询，
   靠"结构化"是走不通的。
