# 分工拼图：不同上下文 → 完整结果，这条路是真的

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-27
> 9 段 × 6K token，每段藏 1 个事实 · Qwen3-1.7B

前面测的"辩论/投票"全失败了。这一轮换掉问题：

> **不是让三个 agent 对同一道题表决，而是让它们各看一块，最后拼起来。**

结果：

| 配置 | 找回事实 |
| --- | ---: |
| 1 个 agent / 24K | **1/9（11%）** |
| **9 个 agent / 各 6K** | **9/9（100%）** |
| 1 个 agent / 30K | 2/9（22%） |

**同样的模型、同样的信息量，分工后全对，不分工基本全错。**

---

## 1. 架构：Map-Reduce

```
        原始语料（54K token，9 段）
                 │ 切分
   ┌─────────────┼─────────────┐
   ▼             ▼             ▼
 worker1       worker2   …   worker9      ← 每人只看 6K，只回答自己那个问题
   │             │             │
   └─────────────┼─────────────┘
                 ▼ 归并（程序做，不是模型）
            完整结果（9/9）
```

```python
# 1. 切分：按 token 均衡，不是按文件数
bins = partition_by_tokens(docs, k=9, budget=6000)

# 2. 每个 worker 只回答自己那块的子问题
facts = [llm(bin_text, question_for(bin)) for bin in bins]

# 3. 归并：程序按 (来源, 主键) 拼装、去重、对账
result = merge(facts)
```

**关键：合并用代码，不用模型。** 模型只负责"从我这块里取事实"，取完就变成结构化数据。

---

## 2. 为什么快：两个机制叠加

单个 agent 的 1/9，可以拆成两部分损失：

| 损失来源 | 数值 | 解释 |
| --- | ---: | --- |
| **覆盖** | 24K 只能装 4/9 段 | 剩下 5 段它**根本没见过** |
| **注意力** | 覆盖内只答对 1/4 = 25% | 24K 长上下文里，单个事实也找不准 |
| **分工后** | 9/9 = 100% | 每段 6K，是注意力最舒服的区间 |

两者相乘：`4/9 × 25% ≈ 11%`，正好是实测的 1/9。

> 分工同时修了两件事：**让模型看全**，以及**让它看得短**。

---

## 3. 一个隐藏的坑：张冠李戴

第一版设计是"每段放 3 个事实"，结果比单 agent 还差。
打印输出后才明白——**不是找不到，是配错了对象**：

```
问：蓝鲸1-1 的密码？  → 5839147   ✅
问：蓝鲸1-2 的密码？  → 5839147   ❌（答案属于 1-1）
问：蓝鲸1-3 的密码？  → 5839147   ❌（还是 1-1）
```

同一段里有 3 个格式相同的"密码"，模型**只记住了一个**，然后套给所有问题。

| 每段事实数 | 9 个 agent 的找回 |
| ---: | ---: |
| 3 个 | **1/9** |
| **1 个** | **9/9** |

> **规则：一个分片里放一个事实。** 同构事实越多，绑定（attribution）越容易错。

---

## 4. 和"辩论"的对比（同一台机器）

| 方法 | 上下文 | 依赖的条件 | 实测 |
| --- | --- | --- | --- |
| 辩论 / 投票 | **相同** | 每个成员 > 50%、错误独立 | ❌ 29–30%（单人 30.5%） |
| MoA 汇总 | 相同 + 候选 | 聚合器不被锚定 | ❌ 30.5%（1.7B 单独 48%） |
| **分工拼图** | **不同** | 信息互补 + 归并正确 | ✅ **9/9 vs 1/9** |

**结论：多 agent 的价值不在"多几个意见"，在"多几双眼睛看不同的地方"。**

## 5. 落地清单

| # | 做法 | 原因 |
| ---: | --- | --- |
| 1 | **按 token 均衡切分**，不按文件数 | 文件大小差 10 倍 |
| 2 | **每片一个事实/一个问题** | 多个同构事实会张冠李戴 |
| 3 | **worker 输出结构化（或原文行）** | 便于程序归并、去重 |
| 4 | **合并用代码** | 模型合会引入新错误 |
| 5 | **带来源字段**（文件名/段落号） | 冲突时可追溯 |
| 6 | 分片大小控制在 **6–8K** | 我们的注意力甜点区（8K 100%） |

### 5.1 什么时候分工没用

- 信息本来就集中在一小段（单次就能看全）；
- 任务需要**全局比较**（"哪个最大"必须看全部）——这时要在归并阶段再做一次全局判断；
- 分片之间的边界把一个事实切开了。

## 7. 结论

1. **分工拼图是有效的**：9 个 agent 各看 6K，找回 9/9；单 agent 看 24K 只有 1/9；
2. **收益来自两处**：覆盖（能看全）+ 注意力（每段更短更准）；
3. **一个分片只放一个事实**：3 个同构事实会让 agent 张冠李戴（1/9）；
4. **归并必须用代码**：模型只做"抽取"，不做"合并"；
5. **这和辩论是两件事**：辩论比"意见"，分工比"覆盖面"——后者才有稳定收益。
