# 真实草稿模型投机：0.6B 当 1.7B 的 draft，为什么反而更慢

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · vLLM 0.34 · 2026-11-26
> target Qwen3-1.7B · draft Qwen3-0.6B · 5 个草稿 token

前天测的 ngram 投机是"抄写加速器"（高重叠负载才有效）。
这一轮换成**真正的小模型当草稿**——理论上这应该是通用加速手段。

结论：**在这个尺寸比下完全无效，而且并发越高越亏。**

> 实测接受率 **34.9%**，而草稿成本约是 target 的 **35%**。
> 投机解码的收益条件是 `接受率 > 草稿成本比`，这里刚好卡在平衡点上。

---

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| target | Qwen3-1.7B（bf16，3.4 GB） |
| draft | Qwen3-0.6B（bf16，1.2 GB） |
| 草稿长度 k | 5 |
| 采样 | `temperature=0`，`ignore_eos=True`，固定输出 128 token |
| 并发 | 1 / 8 / 32 |
| 引擎 | vLLM 0.34，`gpu_memory_utilization=0.78` |

> 草稿与 target 同 tokenizer（Qwen3 系列共用词表），满足投机解码的前提。

---

## 2. 结果

| 并发 | 无投机 | 草稿投机 | 加速比 |
| ---: | ---: | ---: | ---: |
| 1 | 112.4 tok/s | 101.7 tok/s | **0.90×** |
| 8 | 851.8 tok/s | 628.3 tok/s | **0.74×** |
| 32 | 3,032.2 tok/s | 1,605.6 tok/s | **0.53×** |

**全部是负收益，而且并发越高亏得越多。**

### 2.1 接受率（实测）

从 vLLM 的投机指标直接读：

| 指标 | 数值 |
| --- | ---: |
| 接受的草稿 token | 737 |
| 生成的草稿 token | 2,110 |
| **接受率** | **34.9%** |

（另外引擎启动时间从 19 s 涨到 127 s，因为要多加载一份模型 + 多一次 CUDA Graph 捕获。）

---

## 3. 为什么：一个可以算出来的平衡点

投机解码每一步做两件事：

1. 草稿模型**串行生成 k 个 token**；
2. target 模型**一次并行验证** k+1 个位置。

设：

- `c` = 草稿模型单步成本 / target 单步成本 ≈ 参数比 ≈ **0.6/1.7 ≈ 0.35**
- `a` = 接受率（实测 **0.349**）

一步的总成本 ≈ `k·c + 1`，产出 token ≈ `1 + k·a`。

```
加速比 ≈ (1 + k·a) / (1 + k·c)
      = (1 + 5×0.349) / (1 + 5×0.35)
      = 2.745 / 2.75
      ≈ 1.00×
```

**实测 0.90×（并发 1）**——理论值和实测几乎重合。

### 3.1 收益条件

要让投机净赚，必须：

```
k·a > k·c   ⟺   a > c
```

**接受率必须大于草稿成本比。** 本例 `a = 0.349 ≈ c = 0.35`，正好在平衡点，
所以不仅没赚，还因为调度开销倒亏。

### 3.2 并发越高越亏的原因

- 并发 1：草稿串行 5 步，每步都吃不满 GPU；
- 并发 8/32：无投机时 batch 已经把 GPU 喂饱，**投机的验证步把 batch 拆成不规整的变长序列**，
  批处理效率下降；草稿模型也占用额外的显存和调度槽位。

这和前天 ngram 的并发曲线是同一个机制（8 并发交叉，32 并发掉到 0.47×）。

---

## 4. 两种投机的对比

| | ngram（无模型） | 草稿模型（0.6B） |
| --- | --- | --- |
| 原理 | 从 prompt 里找重复片段 | 小模型自回归猜 |
| 适用负载 | **高重叠**（RAG 引文、代码补全、改写） | 理论上通用 |
| 单流收益 | **2.6×**（高重复 prompt）/ 1.37×（自由生成） | 0.90× |
| 8 并发 | 0.99× | 0.74× |
| 32 并发 | 0.47× | 0.53× |
| 额外显存 | 0 | +1.2 GB |
| 启动开销 | 0 | +108 s |

> ngram 的 2.6× 来自"抄写"——输出和输入高度重叠时命中率极高。
> 草稿模型的 34.9% 接受率是**通用负载下的真实水平**，比 ngram 在抄写场景低得多。

---

## 5. 什么情况下草稿投机才划算

### 5.1 尺寸比要够大

`a > c` 意味着**草稿必须远小于 target**：

| target | 合适 draft | 尺寸比 |
| --- | --- | --- |
| 1.7B | ≤0.15B（几乎不存在） | ≤9% |
| 7B | 0.5B | 7% |
| 70B | 1B–3B | 1.5–4% |

**1.7B + 0.6B 是 35%，注定不划算**——这是"小模型推理"的固有困境：
没有足够小的同族草稿可用。

### 5.2 或者用训练过的草稿头

EAGLE / Medusa 这类方法把接受率做到 60–80%，
相当于把 `a` 从 0.35 提到 0.7，此时：

```
加速比 ≈ (1 + 5×0.7) / (1 + 5×0.35) = 4.5 / 2.75 ≈ 1.64×
```

**这才是投机解码真正的用武之地**——但需要额外的训练流程和专用权重（本次没有）。

### 5.3 永远不要在高并发下开投机

无论 ngram 还是草稿模型，8 并发以上都是负收益。
投机是**延迟优化**，不是吞吐优化。

## 7. 结论

1. **0.6B 给 1.7B 做草稿是负收益**（0.90× / 0.74× / 0.53×），不是配置问题，是数学问题；
2. **实测接受率 34.9% ≈ 草稿成本比 35%**，正好卡在 `a = c` 的平衡点，
   与 `(1+ka)/(1+kc) ≈ 1.00` 的理论值吻合；
3. **收益条件是 `接受率 > 草稿成本比`**——这条判据可以省掉大量试错；
4. **小模型（≤3B）几乎没有投机空间**：找不到足够小且同词的草稿；
5. **投机只优化延迟，不优化吞吐**：8 并发以上一律关闭。
