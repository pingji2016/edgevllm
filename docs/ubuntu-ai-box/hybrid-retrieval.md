# RAG 检索升级：换 bge-m3 提 16 pp，混合检索是伪需求

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-26
> 承接 `rag-over-docs.md` / `rag-locate.md`：12 题里 4 题的失败是**召回阶段就没进来**

上一轮定位式 RAG 已到 75% 的瓶颈，问题不在生成、在检索。
这一轮的目标写在文档里：**R@1 从 58% 拉到 70%+**。

结果达到了（**75%**），但过程中**否掉了一个常见假设**：

> **BM25 混合检索在这里完全没用**——加了它，R@1/R@3/R@5 一个数都没变。
> 增益全部来自"更强的嵌入模型 + 重排"。

| 项 | 值 |

| 重排 | bge-reranker-base（278 M），候选 top-20 |

## 3. 为什么混合检索没用

这是本轮最值得记的结论。BM25 和 RRF 在业界几乎是"标配"，但实测**零增益**：

| 问题类型 | BM25 是否应该有用 | 实测 |
| --- | --- | --- |
| 专有名词（`F_NOCACHE`、`Q4_K_M`） | ✅ 应该 | 稠密已经能命中 |
| 数字（`676`、`741928`） | ✅ 应该 | 稠密也命中了 |
| 自然语言问句（"提升多少"） | ❌ 用处小 | BM25 反而更差（50%） |

原因有三条：

1. **查询是自然语言问句，不是关键词串**——BM25 依赖词面重叠，
   而问题里的词（"提升"、"多久"）在文档里未必出现；
2. **bge-m3 本身就覆盖了词面信息**（多语言 + 长上下文训练，
   对专有名词的表示并不弱）；
3. **剩下的失败不是"词面"问题，是"主题稀释"**——20+ 篇 K3 文档互相竞争，
   BM25 同样会把那些相似的 K3 文档排上来，**它和稠密检索错在同一处**。

> 教训：**混合检索不是默认必选项**。它适合"稠密模型明显弱、词面特征强"的场景；
> 一旦换到强嵌入模型，先做 A/B，别直接上融合。

## 5. 成本

| 环节 | 延迟 | 显存 |
| --- | ---: | ---: |
| bge-m3 编码（1 条查询） | **63 ms** | 1.1 GB（bf16） |
| BM25 | 13 ms | 0 |
| RRF 融合 | ~0 ms | 0 |
| reranker（20 候选） | 81 ms | 0.55 GB |
| **合计（不含生成）** | **~145 ms** | 1.65 GB |

对比 bge-small 的 5 ms，bge-m3 慢了 12 倍——但换来 R@1 +16 pp，值。

---

## 6. 推荐流水线

```
查询
 ├─ bge-m3 稠密召回 top-20          （63 ms）
 ├─ bge-reranker 重排 → top-3        （81 ms）
 └─ 切单元（每句拼【章节+表头】）→ 返回原文，或交 LLM 作答
```

**不要加 BM25**（实测无增益、多 13 ms、多一套索引要维护）。

### 6.1 什么时候才考虑混合检索

| 条件 | 建议 |
| --- | --- |
| 稠密模型小（<100 M）或纯英文 | 值得试 BM25 |
| 查询是短关键词 / 商品名 / 错误码 | 值得试 |
| 已用 bge-m3 / 大模型嵌入 | **先测，大概率不需要** |
| 失败原因是"相似文档太多" | 混合检索也救不了，要治理语料 |

## 8. 结论

1. **换 bge-m3：R@1 42% → 58%（+16 pp）**，R@3 +16 pp；
2. **加重排：58% → 75%（+17 pp）**，R@5 到 92%；
3. **加 BM25/RRF：+0 pp**——混合检索在这个语料上是伪需求；
4. **最终 75% / 83% / 92%**，只剩 1 题真正检索失败；
5. **剩下的问题不是检索，是语料治理**（20+ 篇 K3 文档主题重叠）。
