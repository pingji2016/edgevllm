# 端到端与优化：语音助手链路 / CUDA Graph / K3 上的 TTS

> 机器 `pingji-MS-7B89`（RTX 5060 Ti 16 GB）+ K3（RISC-V，8 核）
> 实测日期：2026-11-25 · 配套：[tts-kokoro.md](tts-kokoro.md)、[realtime-services.md](realtime-services.md)

---

## 1. 语音助手全链路：VAD → ASR → LLM → TTS

### 1.1 为什么要把四段拼起来

前面各段都是单独测的（VAD 155 ms、ASR 141 ms、LLM 433 ms、TTS 87 ms），
但**拼在一起的端到端延迟谁也说不准**——进程启动、模型加载、格式转换、数据搬运都会重新计时。

### 1.2 实现上的硬约束

`faster-whisper`（CTranslate2，需 cu12）与 torch（cu132）**不能同进程**，所以：

```
主进程（torch cu13）                    子进程（LD_LIBRARY_PATH=cu12）
┌──────────────────────────┐          ┌──────────────────────────┐
│ ③ LLM（Qwen3-0.6B+LoRA） │◀──文本───│ ① VAD（silero）           │
│ ④ TTS（Kokoro-82M）      │          │ ② ASR（faster-whisper-s） │
└──────────────────────────┘          └──────────────────────────┘
```

### 1.3 实测

输入：13.75 s 中文语音

| 阶段 | 耗时 | 说明 |
| --- | ---: | --- |
| ① VAD 加载 | 377 ms | 一次性 |
| ② ASR 模型加载 | 1,757 ms | 一次性 |
| **VAD+ASR（4 段）** | **2,342 ms** | 含子进程启动 |
| **LLM（48 token）** | **888 ms** | Qwen3-0.6B + LoRA |
| **TTS（6.05 s 音频）** | **100 ms** | Kokoro 稳态 |
| **稳态端到端** | **3.33 s** | 三段相加 |
| 冷启动（含全部加载） | 18.4 s | — |

- 转写结果：`在那之後完全收購那家公司因此保持管理層的一致性利益與即將加入家族的自殘保持一致…`
- 回复：`维持管理层一致性和家族利益，是保持收购后利益的平衡。` ✅
- 合成语音：`~/apps/infer-research/voice_agent/reply.wav`

### 1.4 三个结论

1. **稳态 3.33 s 处理 13.75 s 音频**（4.1× 实时）——但这是"整段处理"，不是流式。
2. **ASR 占了 70% 的时间**（2.34 s）。这里用的是 per-segment 调用（4 次），
   每次都有固定开销；离线整段只要 0.83 s，说明**分段的代价很大**，流式 ASR 必须做增量缓存。
3. **TTS 几乎免费**（100 ms 生成 6 s 语音），LLM 0.6B 也只要 0.89 s。
   **瓶颈明确在 ASR**，优化方向是换更快的模型（tiny/base）或做流式增量。

## 2. vLLM CUDA Graph：我们之前一直关着，损失了 72–84%

### 2.1 背景

之前所有 vLLM 实验都用了 `enforce_eager=True`——因为早期在 sm_120 上担心 CUDA Graph 编译出问题。
这次实测关掉它（启用 CUDA Graph）。

### 2.2 实测（Qwen3-1.7B，同一负载）

| 场景 | eager | **CUDA Graph** | 提升 |
| --- | ---: | ---: | ---: |
| 单流 | 61.1 tok/s | **112.3** | **+83.8%** |
| 8 并发 | 468.6 | **853.0** | **+82.0%** |
| 32 并发 | 1,757.5 | **3,020.0** | **+71.8%** |
| 引擎加载 | 68 s | 51 s | -25% |

### 2.3 结论

- **CUDA Graph 在这张卡上完全可用**（之前的担心是多余的）；
- **提升幅度是"白捡"的**：没有任何算法改动，只是把 kernel 发射的 CPU 开销用图捕获掉；
- **之前所有 vLLM 数字都偏保守**，真实能力是表格右列。

> 原因：decode 每步只有十几毫秒，Python/launch 开销能占到 40%+。
> CUDA Graph 把整串 kernel 录制成一张图，一步 replay，开销几乎归零。
> 这解释了为什么"单流提升最大（+84%）、并发越高提升越小（+72%）"——
> 并发时每步的 kernel 更多，launch 开销占比反而下降。

## 3. Kokoro 82M 跑在 K3（RISC-V）上

### 3.1 关键设计：把 G2P 留在桌面

K3 装不了完整的 Kokoro 依赖链（`soundfile` 需要编译 cffi，RISC-V + Python 3.14 编不过；
`misaki`/`spacy` 更重）。所以**只把声学模型搬过去**：

```
桌面：文本 → G2P（音素串）+ 音色向量 → 存成文件
       ↓ (313 MB 模型 + 174 B 音素串 + 512 KB 音色库)
K3 ：  phonemes.txt + voice.pt + model.pth → KModel(ps, ref_s) → 波形
```

### 3.2 K3 上的环境

| 组件 | 版本 | 备注 |
| --- | --- | --- |
| Python | 3.14.4 | — |
| torch | **2.9.1+debian** | RISC-V 构建，可用 |
| transformers | 5.17.0 | — |
| kokoro | **0.7.16** | 老版本，`KModel(config, model)` 签名（无 `repo_id`） |
| onnxruntime | 1.24.2+spacemit.a1 | SpacemiT 优化版（本次未用） |

**两个适配技巧：**

1. **stub 掉 misaki**：`kokoro/__init__.py` 会 import `misaki`（G2P 用），
   但我们只需要 `KModel`。在 `sys.modules` 里塞三个空模块即可绕过：

   ```python
   for n in ("misaki", "misaki.en", "misaki.espeak"):
       sys.modules[n] = types.ModuleType(n)
   from kokoro.model import KModel
   ```

2. **用 `wave` 代替 `soundfile`**（后者装不上）：

   ```python
   pcm = (np.clip(a, -1, 1) * 32767).astype(np.int16)
   w = wave.open("out.wav", "wb"); ...
   ```

### 3.3 实测

| 指标 | K3 | 桌面（对照） |
| --- | ---: | ---: |
| 模型加载 | 4.4 s | 12.5 s（含首次） |
| 参数量 | 81.8 M | 81.8 M |
| 音频时长 | 6.22 s | 6.22 s |
| 生成耗时 | **12,975 ms** | 1,089 ms（首调）/ 83 ms（稳态） |
| **RTF** | **2.084（0.48× 实时）** | 0.175（5.7×）/ 0.014（70×） |

**输出质量：与桌面逐字一致**（同一模型、确定性推理），ASR 回听：

```
目标: 端侧推理部署说明：解码速度五十五点三，每秒钟六十二个。
K3:   端策推理部署說明,解碼速度55.3每秒中62个。
```

### 3.4 结论

| 问题 | 答案 |
| --- | --- |
| K3 能跑 82M TTS 吗 | ✅ 能，4.4 s 加载，输出正确 |
| 能实时吗 | ❌ **0.48× 实时**（6.2 s 语音要 13 s） |
| 适合什么 | **离线预生成**（提示音、告警语、导航播报）——生成一次存起来反复用 |
| 不适合什么 | 实时对话（需要 <1× 实时） |

**K3 与桌面的差距：约 12–150 倍**（取决于桌面是否计入稳态）。
这说明**把大模型放桌面、把固定语音放板子**是当前最合理的分工。

## 4. 三项合起来的一张总表

| 链路 / 配置 | 延迟 | 说明 |
| --- | ---: | --- |
| 语音助手（VAD→ASR→LLM→TTS） | **3.33 s** / 13.75 s 音频 | 瓶颈在 ASR（2.34 s） |
| vLLM 单流（CUDA Graph） | **112.3 tok/s** | 比 eager 快 84% |
| vLLM 32 并发 | **3,020 tok/s** | 比 eager 快 72% |
| Kokoro 桌面（稳态） | **70× 实时** | — |
| Kokoro K3 | **0.48× 实时** | 只能离线预生成 |

**优化优先级（基于本轮数据）：**

1. **开 CUDA Graph**（+72–84%，零成本）
2. **ASR 换小模型或做增量流式**（当前占端到端 70%）
3. **TTS 放桌面、固定语句放 K3**（0.48× 实时只够预生成）
