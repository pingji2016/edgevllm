# 第一部分 原理

## 1. 三个上限：先算物理账，再谈优化

一块卡决定能跑多快，只有三个数：**显存带宽、算力、显存容量**。
RTX 5060 Ti 16 GB 的三个上限：

| 上限 | 数值 | 来源 |
| --- | ---: | --- |
| 显存带宽 | **448 GB/s** | GDDR7 28 Gbps × 128-bit |
| 算力（bf16 GEMM） | 数十 TFLOPS（ncu 实测 ~50 TFLOPS，SM 占用 48.9%）| 【实测】 |
| 显存 | 16 GB（可用 ~15.5 GB）| — |

### 1.1 解码是带宽问题

自回归解码每生成一个 token，要把**全部权重读一遍**（batch=1 时没有复用）。
所以解码速度有一个硬上限：

```
tokens/s ≤ 带宽 ÷ 权重体积
```

| 模型 | 精度 | 权重 | 理论上限 | 【实测】 |
| --- | --- | ---: | ---: | ---: |
| Qwen3-0.6B | bf16 | 1.2 GB | 373 tok/s | — |
| **Qwen3-1.7B** | bf16 | 3.4 GB | **131.8 tok/s** | **112.4（85%）** |
| Qwen3-1.7B | Int8 | 1.7 GB | 263.5 tok/s | **171.9（65%）** |
| Qwen3-8B | bf16 | 16 GB | 28 tok/s | 放不下 |

两个结论：

1. **bf16 的 85% 已经接近极限**——再怎么调 kernel 也就多 15%；
2. **Int8 只兑现 65%**——因为反量化（INT8→bf16）要多读 scale、多跑一遍 kernel，
   有效带宽打折。这解释了为什么"参数量减半"不等于"速度翻倍"（实测 1.53×，不是 2×）。

> **判据**：看到"某优化快 3 倍"，先问它有没有超过 `带宽 ÷ 权重` 这个上限。
> 超过了，一定是改变了 batch 或命中了缓存，不是"kernel 更好"。

### 1.2 预填充是算力问题

Prefill（处理 prompt）是并行矩阵乘，瓶颈是算力：

```
每个 token 的线性层 FLOPs ≈ 2 × 参数量
```

1.7B 模型：每个 token 约 **3.4 GFLOP**。

【实测】8K 上下文时 prefill 吞吐 **14.4K tok/s**，对应有效算力：

```
14,400 × 3.4 GFLOP ≈ 49 TFLOPS
```

**这和 ncu 测到的 ~50 TFLOPS 完全吻合**——说明 8K 时 GPU 已经被喂饱，
瓶颈就是算力，不是调度。

### 1.3 为什么 8K 时吞吐最高

| 上下文 | prefill 吞吐【实测】 | 解释 |
| ---: | ---: | --- |
| 2K | 8.3–11.2K tok/s | 规模太小，kernel 启动/占用率不足 |
| 4K | 10.5–14.6K | 逐渐喂饱 |
| **8K** | **14.4K（峰值）** | 算力打满 |
| 16K | 9.0–13.5K | attention 占比上升 |
| 32K | **6.5K** | attention 的 O(T²) 主导 |

## 2. 显存账本

### 2.1 总账公式

```
M_total = M_weights + M_kv + M_activations + M_overhead
```

vLLM 里的 `gpu_memory_utilization` 约束的是 `M_total / 显卡容量`。

### 2.2 权重

| 模型 | bf16 | Int8 | NF4 |
| --- | ---: | ---: | ---: |
| 0.6B | 1.2 GB | 0.6 GB | 0.35 GB |
| 1.7B | 3.4 GB | 1.7 GB | 0.9 GB |
| 8B | 16 GB | 8 GB | 4.5 GB |

### 2.3 KV 缓存（GQA）

每个 token 的 KV 占用：

```
KV/token = 2 × 层数 × KV头数 × head_dim × 字节数
```

Qwen3-1.7B：28 层、8 个 KV 头、head_dim 128、bf16 → 

```
2 × 28 × 8 × 128 × 2 = 114,688 B ≈ 112 KB/token
```

| 上下文 | KV 占用 |
| ---: | ---: |
| 4K | 0.46 GB |
| 8K | 0.92 GB |
| 16K | 1.84 GB |
| 32K | **3.67 GB** |

### 2.4 能开多少并发

```
并发数 ≈ KV 预算 ÷ (上下文长度 × 112 KB)
```

16 GB 卡、1.7B bf16、0.80 利用率：

```
总预算 12.4 GB − 权重 3.4 GB − 激活 ~1.5 GB ≈ 7.5 GB 给 KV
→ 总容量 ≈ 7.5 GB ÷ 112 KB ≈ 67,000 tokens
```

| 上下文 | 最大并发 |
| ---: | ---: |
| 4K | ~16 路 |
| 8K | ~8 路 |
| 16K | ~4 路 |
| 32K | **~2 路** |

【实测】vLLM 在 32K 配置下报告 `GPU KV cache size: 74,752 tokens`，
`Maximum concurrency for 33,280 tokens per request: 2.25x`——与估算一致。

> **推论**：长上下文和并发是**直接抢资源**的。
> "支持 32K"在生产上通常意味着"只能服务 2 个用户"。

## 3. 引擎到底做了什么

| 机制 | 解决什么 | 代价 | 【实测】收益 |
| --- | --- | --- | --- |
| **PagedAttention** | KV 按块分配，消除碎片 | 块表间接寻址 | 高并发基础 |
| **连续批处理** | 请求随到随算，不等整批 | 调度复杂 | 32 并发 4.4K tok/s |
| **CUDA Graph** | 消除每步的 kernel 启动开销 | 形状固定 | 单流 **+245%** |
| **前缀缓存** | 相同前缀复用 KV | 占显存 | 4K 省 **49%**、16K 省 **89%** |
| **FP8 KV** | KV 减半 → 并发翻倍 | 轻微精度损失 | 32 并发 **+6%** |
| **Chunked prefill** | 长 prompt 切块，与 decode 交错 | 首 token 略慢 | 降低长请求的阻塞 |

### 3.1 CUDA Graph 为什么值 3 倍

【实测】eager 模式 61.3 tok/s、graph 模式 112.3 tok/s，**输出逐字一致**。

小模型单步的物理时间 ≈ 8.9 ms，但每步要发 **~290 个 kernel**，
每个 launch ~25 µs → **7.25 ms 是纯启动开销**。
CUDA Graph 把这 290 次 launch 折叠成一次图回放，于是：

```
16.3 ms/token（eager） → 8.9 ms/token（graph）
```

> 这解释了 CUDA Graph 的收益边界：
> **小模型 + batch 1 → 70–85%**（启动占比高）；
> **大模型 → 20–40%**（计算本身占主导）；
> **高并发 → 10–25%**（每步算得多，启动摊薄）。

### 3.2 前缀缓存为什么能省 89%

Prefill 的成本与**新 token 数**成正比。4K 上下文里如果前 3.5K 命中缓存，
只需算 0.5K → 省 87.5%。【实测】4K 省 49%、16K 省 89%（命中率不同）。

### 3.3 FP8 KV 的真实作用

单流 decode 的瓶颈是**读权重**（1.7 GB），KV 只有几十 MB，压它没用（+1%）。
但 KV 减半让**块数翻倍**，并发能力上升（32 并发 +6%）。

> 同一个优化，对不同负载的作用完全不同——这就是为什么必须分场景测。

## 4. 量化：数学、误差来源与损伤边界

### 4.1 三种格式

| 格式 | 位数 | 做法 | 误差量级 |
| --- | ---: | --- | --- |
| **INT8（GPTQ）** | 8 | 对称 per-channel：`w_q = round(w/s)`，`s = max|w|/127` | ≤ 0.4% |
| **NF4** | 4 | 16 个按 N(0,1) 分位点取值 + 64 元素块 absmax | ~1–2% |
| **GGUF Q4_K_M** | ~4.5 | 超块（256）+ 子块（32）双尺度 | ~1% |

### 4.2 为什么 Int8 几乎无损

每层权重有 256 个量化级，步长 `s = max|w|/127`。
单个权重的绝对误差 ≤ `s/2`，相对误差通常在 **0.2–0.4%**。

一层有几千个权重，误差**随机抵消**（不是同向累加），
所以整层输出的相对扰动仍在 0.4% 量级——远小于 bf16 本身的表示误差累积。

【实测】Qwen3-1.7B：

| 任务 | bf16 | Int8 |
| --- | ---: | ---: |
| 算术（三位×两位） | 50% | **52%**（噪声内） |
| JSON 抽取 | 100% | 100% |
| 8K needle | 3/4 | 3/4 |

### 4.3 为什么 NF4 会伤算术

4 bit 只有 16 个量化级。对一个三位数×两位数的乘法，
**结果的最后一位**要求中间累加的相对精度在 `1e-4` 量级；
而 NF4 的 1–2% 权重扰动，足以让末位翻车。

【实测】300 题配对（同一批题、同一解码方式）：

| | bf16 | NF4 |
| --- | ---: | ---: |
| 准确率 | **49.0%** | **42.3%** |
| 只有前者对 | 32 题 | — |
| 只有后者对 | — | 12 题 |
| McNemar z | **3.02**（显著） | — |

但在 JSON（结构）和 needle（位置）上**没有退化**：

> **量化伤的是"逐位精确"，不是"格式"或"检索"。**

### 4.4 显存的账不划算

| | bf16 | NF4 | 节省 |
| --- | ---: | ---: | ---: |
| 权重 | 3.4 GB | 0.9 GB | 2.5 GB |
| **峰值（batch 8）** | 6.53 GB | 4.58 GB | **1.95 GB** |

因为峰值里还有 activations 和 **6400×词表 logits**，这部分不随权重量化缩小。
在 16 GB 卡上，省下的 2 GB 通常换不来一个更大的模型。

## 5. 投机解码：一个可以推导的收益条件

### 5.1 模型

一"步"投机解码做两件事：

1. 草稿串行生成 `k` 个 token，成本 `k·c`（`c` = 草稿/目标 的单步成本比）；
2. 目标模型一次验证 `k+1` 个位置，成本 `1`。

产出 token 数 = `1 + k·a`（`a` = 接受率）。

```
加速比 ≈ (1 + k·a) / (1 + k·c)
```

**收益条件：**

```
a > c
```

### 5.2 三种实现的 c

| 实现 | c | 典型 a | 结论 |
| --- | ---: | ---: | --- |
| **ngram**（从 prompt 抄） | ≈ 0 | 高重叠时 0.5–0.8 | 抄写场景极强，通用场景弱 |
| **草稿模型** | 参数量比 | 0.3–0.5 | 需要草稿 ≤ 目标 1/10 |
| **EAGLE / Medusa** | ≈ 0.05 | 0.6–0.8 | 唯一能稳定 2× 的路线 |

### 5.3 【实测】验证

**ngram**（Qwen3-1.7B，GPTQ-Int8，fp8 KV）：

| 并发 | 无投机 | +ngram | 比值 |
| ---: | ---: | ---: | ---: |
| 1 | 173.7 | 457.8 | **2.64×** |
| 4 | 685.0 | 1,427.1 | 2.08× |
| 8 | 1,328.8 | 1,321.7 | **0.99×**（交叉点）|
| 32 | 4,409.0 | 2,058.4 | 0.47× |
| 64 | 6,578.3 | 2,293.0 | 0.35× |

**草稿模型**（0.6B → 1.7B，k=5）：

| 并发 | 无投机 | +草稿 | 比值 |
| ---: | ---: | ---: | ---: |
| 1 | 112.4 | 101.7 | 0.90× |
| 8 | 851.8 | 628.3 | 0.74× |
| 32 | 3,032.2 | 1,605.6 | 0.53× |

实测接受率 **34.9%**，草稿成本比 **≈ 0.35**：

```
(1 + 5×0.349) / (1 + 5×0.35) = 2.745 / 2.75 ≈ 1.00×
```

与实测 0.90× 吻合。**a ≈ c 时，投机不仅不赚，还要付调度开销。**

### 5.4 为什么高并发一定亏

低并发时 GPU 空转，投机是用**闲置算力**换步数；
高并发时 batch 已经把 GPU 喂饱，投机的验证步要把 batch 拆成
**变长的、不规整的序列**，批处理效率下降，吞吐反而掉。

> **投机是延迟优化，不是吞吐优化。** 8 并发以上一律关闭。

### 5.5 一个未验证的预测

投机在**高并发 + 长输出**时还有一个隐性成本：草稿 token 也要占 KV。
如果上下文已经接近显存上限，投机可能直接触发 OOM 或降低并发。
本次未单独测，理论上应成立。

## 6. 长上下文：为什么 32K 会崩

### 6.1 算力的两块

Prefill 的 FLOPs 由两部分组成：

```
线性层：2 × N × T                    （随 T 线性）
注意力：4 × L × T² × d_model          （随 T 平方）
```

两者之比：

```
注意力 / 线性 = (4·L·d_model·T²) / (2·N·T) = 6.75e-5 × T
```

| 上下文 | 注意力占比 |
| ---: | ---: |
| 8K | **35%** |
| 32K | **69%** |

**这就是 32K prefill 慢 2.2 倍的原因**：大部分时间花在 O(T²) 的注意力上，
而注意力的 kernel 效率低于大矩阵乘。

### 6.2 解码也会被拖慢（【推导】，待复核）

解码时每个 token 要读：

```
权重（3.4 GB）+ KV（112 KB × T）
```

| 上下文 | 每 token 读取 | 理论解码 |
| ---: | ---: | ---: |
| 2K | 3.63 GB | 123 tok/s |
| 8K | 4.32 GB | 104 tok/s |
| 32K | **7.07 GB** | **63 tok/s** |

**长上下文会把解码速度砍半**——因为 KV 读放大。
（本次没有干净地测到这一点，之前的 32K decode 数据被判定为无效，这里只给预测。）

### 6.3 质量为什么崩

【实测】needle 命中率：

| 长度 | 2K | 4K | 8K | 16K | 24K | 32K |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 准确率 | 100% | 100% | 100% | 78% | 67% | **11%** |

32K 恰好是 Qwen3-1.7B 的**原生训练长度**。这说明：

> **"训练长度"是能力悬崖，不是能力平台。**
> 模型在训练长度的边缘最脆弱，因为位置编码外推、注意力分布都到了极限。

失败方式也值得注意：它输出的不是"不知道"，而是**语料里邻近的数字**（`123456`、`128`）。
**静默错误比拒答危险得多。**

## 7. RAG：双塔、交叉编码器与切片的语义完整性

### 7.1 两种检索器的本质区别

| | 双塔（bi-encoder） | 交叉编码器（cross-encoder） |
| --- | --- | --- |
| 计算 | `cos(E(q), E(d))` | `f([q; d])` |
| 预计算 | 文档向量可离线算 | 不能，必须逐对跑 |
| 复杂度 | 查询 O(1) | 查询 O(候选数) |
| 精度 | 较低（无交互） | 高（全交互） |
| 用途 | **召回**（top-100） | **重排**（top-20 → top-3） |

**正确用法是两级**：双塔负责"别漏"，交叉编码器负责"排序"。

【实测】我们自己的 12 题：

| 方案 | R@1 | R@3 | R@5 |
| --- | ---: | ---: | ---: |
| bge-small 双塔 | 42% | 67% | 67% |
| + 交叉编码器 | 58% | 75% | 75% |
| bge-m3 双塔 | 58% | 83% | 83% |
| **+ 交叉编码器** | **75%** | 83% | **92%** |

两级各贡献 +16～17 pp。

### 7.2 为什么"混合检索"可能是伪需求

BM25 与向量的融合（RRF）是常见做法：

```
score(d) = Σ 1 / (k + rank_i(d))      k=60
```

但【实测】在 bge-m3 之上加 BM25：**R@1/R@3/R@5 一个数都没变**。

原因：

1. 查询是**自然语言问句**（"提升多少"），BM25 依赖词面重叠，问句里的词文档里未必有；
2. bge-m3 已经覆盖了词面信息（多语言 + 长上下文训练）；
3. 剩下的失败是**主题稀释**——20+ 篇同主题文档互相竞争，
   BM25 会把同样的文档排上来，**和稠密检索错在同一处**。

> **判据**：混合检索适合"嵌入模型弱 + 查询是关键词"的场景。
> 换了强嵌入之后，先做 A/B，别默认加。

### 7.3 切片的语义完整性

一个切片必须能**独立回答一个问题**。我们用 12 题做了消融：

| 切片方式 | 正确 |
| --- | ---: |
| 裸句子（含表格行） | 4/12 |
| + 章节标题 | 5/12 |
| **+ 章节标题 + 表头** | **6/12** |

原因：markdown 表格的一行 `| Q4_K_M | 221.8 |` **没有主语、没有列名**，
脱离表头后无法判断数字的含义。

> **规则**：句子级/行级检索时，每个单元前面必须拼上
> **【章节路径 + 表头】**，否则切得越细，语义丢得越多。

### 7.4 定位式：让模型指路，程序抄写

小模型（1.7B）自己复述数字会错（385.9 vs 221.8）。
改成"模型只输出句子编号，程序取原文"，准确率不变但**延迟从 619 ms 降到 17 ms**，
且答案**逐字可溯源**。

两个前提：

1. 输出空间要压到最小（只输出一个数字，否则它会无视格式——实测两行格式 0/12 服从）；
2. 单元要带上下文（见 7.3）。

## 8. 训练与对齐：四种方法的梯度长什么样

### 8.1 SFT

```
L = −Σ log π(y_t | x, y_<t)
```

梯度对 logit 的影响：`∂L/∂z = p − 1`（正确 token 处）。

**含义**：模型越确信，梯度越小。这是理解 RFT 为什么失败的关键。

### 8.2 DPO

```
L = −log σ( β[log π(y_w)/π_ref(y_w) − log π(y_l)/π_ref(y_l)] )
```

它不需要奖励模型，直接比较"好回答"和"坏回答"的相对概率。

### 8.3 GRPO

对同一道题采样 G 个回答，算组内相对优势：

```
Â_i = (r_i − mean(r)) / (std(r) + ε)
L = −mean( Â_i · Σ_t log π(a_t | s, a_<t) )
```

（通常再加 `β·KL(π‖π_ref)` 防止跑偏。）

**关键**：负优势会**压低错误的 token**。这是它和 SFT 的本质区别。

### 8.4 RFT（拒绝采样微调）

```
采样 → 只保留答对的 → 对这些样本做 SFT
```

听起来合理，但【实测】几乎无效（+2 pp，噪声内）。原因就写在 8.1 的梯度里：

- 被保留下来的样本是模型**自己生成的正确样本**，`p ≈ 1`；
- 梯度 `p − 1 ≈ 0`；
- 决定准确率边界的是**错题**，而 RFT 把错题全丢了。

【实测】训练 loss 一路掉到 **0.0000**，就是"没有梯度"的直接证据。

### 8.5 为什么 RL 会塌缩到"众数"

无 KL 约束时，策略会收敛到**奖励期望最高的单点**。
自然分布下（0–9 加 0–9），和为 9 的概率是 **10%**，
所以"永远答 9"的期望奖励是 10%，而真正会算也只有 14%——
两者差距小于策略梯度的信噪比，优化器选了更容易的局部最优。

【实测】30M 模型 400 步后：熵 **0.00 bit**、200 题全部答 9、
均衡题集准确率 **5.3%（= 随机）**、剔除 sum=9 后 **0%**。

加 KL(0.05) 后熵回到 **3.92 bit**，均衡题集 **13.5%**（基线 6.7%，随机 5.3%）。

### 8.6 容量决定 RL 有没有东西可放大

| | minimind-30M | Qwen3-1.7B |
| --- | ---: | ---: |
| 任务 | 一位数加法 | 三位×两位 |
| 基线 | **0%** | 47% |
| RL 后 | 5.3%（塌缩） | **60%（+13 pp）** |
| 现象 | 熵归零 | 精度提升、无塌缩 |

> **RL 修的是"精度"，不是"能力"。**
> 1.7B 的 +13 pp 来自把"误差<1%"的 85% 修到 98.5%，
> 而不是学会了新算法（两步运算仍然只有 5%）。

## 9. 评测方法论：怎么让数字可信

### 9.1 二项分布的噪声

```
SE = sqrt(p(1−p)/n)
```

| n | p=0.5 时的 ±1σ |
| ---: | ---: |
| 100 | ±5.0 pp |
| 200 | ±3.5 pp |
| 300 | ±2.9 pp |

**所以"提升 2 pp"在 100 题上毫无意义。** 我们实测过：
同一模型、同一题集，批量解码与逐条解码差 **3.5 pp**。

### 9.2 配对检验（McNemar）

同一批题上比较两个模型，看**不一致的四格**：

```
z = (b − c) / sqrt(b + c)
```

`b` = 只有 A 对的题数，`c` = 只有 B 对的题数。

【实测】bf16 vs NF4：b=32、c=12 → `z = 20/√44 = 3.02`（p<0.01，显著）。

> 配对检验比"比两个准确率"灵敏得多——同样的数据，边际对比可能不显著。

### 9.3 oracle@N：测"能力上限"

N 次采样里只要有一次对就算对。

| 用途 | 判据 |
| --- | --- |
| oracle@N 远高于 N=1 | 模型"会但不确定"→ **投票有用** |
| oracle@N 几乎不涨 | 能力问题 → **投票是浪费算力** |

【实测】算术题：基座 oracle@32 只有 51%（N=1 48%），
所以投票 −1 pp；而 LoRA 的 oracle@32 是 68.5%，投票仍只有 57%
（正确答案不是众数）。

### 9.4 众数陷阱与均衡题集

自然题目分布下，"永远答某个众数"就能拿到可观分数。
必须构造**均衡题集**（每个答案等概率）才能测出真实能力。

【实测】0–9 加 0–9：和为 9 占 10%，随机猜占 5.3%。
不设均衡题集，会把 reward hacking 当成"学到了"。

### 9.5 判据归一化

- 千分位逗号：`1,780,737` vs 关键词 `178` → 误判；
- 中英文数字：`0.48` vs `0.49` 可能是同一个物理量；
- 题目歧义：同一指标有多个正确版本（eager / graph / 不同并发）。

**自动评测的错误，一半来自判据，不来自模型。**

## 13. Runbook 4：给一块新卡做上限标定

拿到任何新卡，按这个顺序 30 分钟能算出"能跑多快"。

### 13.1 测带宽

```python
import torch, time
x = torch.empty(1<<28, dtype=torch.uint8, device="cuda")   # 256 MB
y = torch.empty_like(x)
for _ in range(3): y.copy_(x)          # 预热
torch.cuda.synchronize(); t = time.time()
for _ in range(20): y.copy_(x)
torch.cuda.synchronize()
gb = 2 * x.numel() * 20 / 1e9
print(f"{gb/(time.time()-t):.0f} GB/s")
```

### 13.2 测算力

```python
a = torch.randn(8192, 8192, dtype=torch.bfloat16, device="cuda")
for _ in range(3): a @ a
torch.cuda.synchronize(); t = time.time()
for _ in range(10): a @ a
torch.cuda.synchronize()
tflops = 2 * 8192**3 * 10 / (time.time()-t) / 1e12
print(f"{tflops:.0f} TFLOPS")
```

### 13.3 预测并验证

```
解码上限 ≈ 带宽 ÷ 权重
预填充上限 ≈ 算力 ÷ (2 × 参数量)
并发上限 ≈ (显存 × 0.8 − 权重 − 激活) ÷ (上下文 × KV/token)
```

跑一个 1.7B 验证：如果实测解码达到预测的 80% 以上，说明环境正常；
低于 60%，先查 `enforce_eager` 和常驻进程。
