# 长上下文实测：1.7B 在 16 GB 卡上的安全线是 16K

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · vLLM 0.34 · 2026-11-26
> 模型 Qwen3-1.7B（bf16），语料用我们自己写的 20 万字文档

前面的实验测过 prefill / decode 的**速度曲线**，但没测过**质量**：
上下文塞到 32K，模型还真看得见里面的事实吗？

答案分两半：

> **16K 以内基本可靠；20K 开始掉；32K 直接崩（1/9），
> 而且失败方式不是"说不知道"，是"抓一个旁边的数字，还答得很自信"。**

---

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| 模型 | Qwen3-1.7B bf16（原生 32K 上下文） |
| 引擎 | vLLM 0.34，`max_model_len=33280`，`gpu_memory_utilization=0.80` |
| 语料 | `edgevllm/docs/ubuntu-ai-box` 的 19 篇文档（555 个段落） |
| 长度 | 2K / 4K / 8K / 16K / 20K / 24K / 28K / 32K |
| 深度 | 10% / 50% / 90%（needle 在 haystack 中的位置） |
| 重复 | 每个组合 2–3 个随机种子 |
| 解码 | 贪心，`max_tokens=12` |
| Needle | 「机房代号“蓝鲸”的访问密码是 741928」 |
| 判据 | 输出里是否出现 `741928`（逐字） |

Needle 是**唯一**的正确暗号，语料里故意保留了大量真实数字（实测数据）作为干扰项。

---

## 2. 准确率

| 上下文长度 | 10% 深度 | 50% 深度 | 90% 深度 | 合计 |
| ---: | ---: | ---: | ---: | ---: |
| 2K | 3/3 | 3/3 | 3/3 | **9/9（100%）** |
| 4K | 3/3 | 3/3 | 3/3 | **9/9（100%）** |
| 8K | 3/3 | 3/3 | 3/3 | **9/9（100%）** |
| 16K | 3/3 | 2/3 | 2/3 | 7/9（78%） |
| 20K | 1/2 | 2/2 | 2/2 | 5/6（83%） |
| 24K | 1/2 | 1/2 | 2/2 | 4/6（67%） |
| 28K | 1/2 | 2/2 | 1/2 | 4/6（67%） |
| **32K** | **0/3** | **0/3** | **1/3** | **1/9（11%）** |

### 2.1 两条线

- **安全线 = 16K**：8K 以内 100%，16K 开始出现偶发失败；
- **崩溃点 = 32K**：即使 needle 放在最末尾（90%，最近的位置），也只有 1/3 命中。

> 注意 32K 是 Qwen3-1.7B 的**原生训练长度**。这说明"标称 32K"不等于"32K 可靠"，
> 训练长度边缘正好是能力悬崖。

### 2.2 "lost in the middle" 在这里不明显

经典的"中间信息丢失"现象：开头和结尾记得好，中间差。
本次数据只有很弱的迹象（16K 时 10% 深度 3/3，50%/90% 各 2/3），
但每个格子只有 2–3 个样本，**不足以确认**。

真正的现象是**整体长度崩塌**，而不是位置效应。

---

## 3. 失败方式：抓错数字，而不是说不知道

32K 和 20K 的失败输出：

| 长度 | 深度 | 输出 | 解释 |
| --- | ---: | --- | --- |
| 32K | 10% | `123456` | 语料里别的数字（看着就像"密码"） |
| 32K | 50% | `128` | 语料里大量出现的维度数字 |
| 28K | 10% | `18291` | 拼凑的数字 |
| 20K | 10% | `123456` | 同上 |

**这比"不知道"更危险**：输出格式完全正常、语气确定，
只有对照原文才能发现是错的。

> 对生产系统，这意味着**长上下文不能替代检索**：
> 塞满 32K 的失败率是 89%，而失败是静默的。

---

## 4. 速度与显存

### 4.1 Prefill（batch=1，首 token 延迟）

| 上下文 | prefill 耗时 | 吞吐 |
| ---: | ---: | ---: |
| 2K | 0.18–0.24 s | 8.3–11.2K tok/s |
| 4K | 0.28–0.39 s | 10.5–14.6K tok/s |
| 8K | 0.54–0.78 s | **14.4K tok/s（峰值）** |
| 16K | 1.2–1.8 s | 9.0–13.5K tok/s |
| 20K | 1.7–2.6 s | 7.8–11.9K tok/s |
| 24K | 2.3–3.2 s | 7.6–10.9K tok/s |
| 32K | **4.4–5.0 s** | **6.5–7.4K tok/s** |

- 8K 时吞吐最高（GPU 喂饱了）；
- 32K 时吞吐掉到 6.5K，**prefill 要 5 秒**——用户问一句话，先等 5 秒。

### 4.2 KV 缓存

| 项 | 值 |
| --- | ---: |
| 每 token KV | **112 KB**（2 × 28 层 × 8 KV 头 × 128 维 × 2 B） |
| 16K 上下文 | 1.84 GB |
| 32K 上下文 | **3.67 GB** |
| vLLM 实分配 | **74,752 token**（≈ 8.4 GB） |
| 32K 时最大并发 | **2.25 路** |

> 16 GB 卡上，1.7B + 32K 上下文只能同时服务 **2 个请求**。
> 想上并发，要么减上下文，要么开 FP8 KV（昨天实测减半）。

---

## 5. 实用建议

| 场景 | 建议 |
| --- | --- |
| 文档问答 / RAG | **别把整篇塞进去**：16K 以内 + 检索，失败率从 89% 降到个位数 |
| 长对话 | 超过 8K 就做摘要压缩，别指望模型自己"记得" |
| 批处理 / 高并发 | 上下文 ≤ 8K，并发能上 8 路 |
| 必须 32K | 换更大模型，或开 FP8 KV + 只留 1–2 路并发 |

### 5.1 为什么"检索"比"长上下文"划算

| | 32K 全塞 | 4K 检索后塞 |
| --- | ---: | ---: |
| 准确率 | 11% | 上一轮 RAG 的 R@3 75%+ |
| prefill | 5 s | 0.3 s |
| 并发 | 2.25 路 | 20+ 路 |

**同样的 GPU，检索方案的准确率和延迟都好一个数量级。**

## 6. 复现

```bash
cd ~/apps/infer-engines

# 主长度扫描（2K–32K）
python needle.py

# 中间段加密（20K/24K/28K）
python needle_mid.py

# 产物
#   needle.json  needle_mid.json
```

> 跑前停 `vlm-server`：`echo 123456 | sudo -S systemctl stop vlm-server`

### 6.1 本实验的局限

- 每个格子只有 2–3 个种子，16K–28K 的差异在噪声范围内；
- 只有 1 个 needle，是"大海捞针"的**简单版**（真实任务常需多跳）；
- 语料是中文技术文档，英文/代码的比例会影响 token 密度。

结论里最稳的是两个端点：**≤8K 100%，32K 崩溃**。

---

## 7. 结论

1. **标称 32K ≠ 可用 32K**：Qwen3-1.7B 在原生上限处只有 **11%** 命中率；
2. **安全线是 16K**（保守 8K），超过后准确率单调下滑；
3. **失败是静默的**：模型输出一个看起来合理的错误数字（`123456`、`128`），
   而不是说"没找到"——这对生产系统是最危险的一种失败；
4. **32K 的代价**：prefill 5 秒、KV 3.67 GB、并发只有 2.25 路；
5. **长上下文不能替代检索**：4K 检索方案在准确率、延迟、并发上全面占优。
