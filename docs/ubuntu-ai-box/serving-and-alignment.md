## 1. vLLM 多 LoRA 服务（Qwen3-0.6B + 自训 adapter）

配置：`enable_lora=True, max_lora_rank=16, max_loras=2`，adapter 来自上一轮 LoRA 微调。

| 场景 | base | +LoRA | 变化 |
| --- | ---: | ---: | ---: |
| 单请求 | 40.3 tok/s | 23.3 tok/s | **-42.3%** |
| 8 并发 | 297.3 tok/s | 127.9 tok/s | **-57.0%** |

**两个结论：**

1. **vLLM 的 LoRA 路径在这个尺寸上开销巨大**（-42% ~ -57%）。
   原因：LoRA 层的 kernel（Punica/SGMV 一类）是为"大模型 + 多 adapter 并发"设计的，
   在 0.6B 这种小模型上，额外 kernel 启动与 gather 开销无法被矩阵乘掩盖。
2. **60 步的 adapter 会退化输出**：

   | | 输出 |
   | --- | --- |
   | base | 显存带宽是指显存中每个数据位的传输速率，通常以每秒每比特（bps）为单位… |
   | +LoRA(60步) | 显存带宽是指显卡的显存带宽，即显卡的显存容量与显存带宽的比值。显存带宽越高，显卡的显存容量越大…（重复） |

   **欠训练的 adapter 不只是"没学到"，而是会主动伤害**——因为 LoRA 的 B 矩阵已经开始
   把隐空间往某个方向推，但还没学到稳定的映射。生产上必须用 eval 集卡住"上线门槛"。

## 2. 前缀缓存曲线（TTFT vs 前缀长度）

同一段前缀连续请求两次，对比"命中缓存"与"关掉缓存"的 TTFT（3 次取最小）：

| 前缀长度 | 命中 | 未命中 | 节省 |
| ---: | ---: | ---: | ---: |
| 1,035 token | 125.2 ms | 126.3 ms | 1% |
| 4,107 token | 128.6 ms | 250.0 ms | **49%** |
| 16,395 token | 141.1 ms | 1,265.0 ms | **89%** |

**结论：前缀缓存把 O(L) 的 prefill 变成了 O(1)。**

- 命中时 TTFT 几乎与前缀长度无关（125 → 141 ms，只涨了 13%）
- 未命中时 TTFT 随长度线性增长（126 → 1265 ms，正好 10×，与 token 数比例一致）
- 对 RAG / 长 system prompt / 多轮对话，这是**白送的收益**

## 3. DPO 对齐（minimind 30M）

### 3.1 数据（合成）

本地没有 DPO 数据，从 `sft_t2t_mini.jsonl` 合成：
`chosen` = 原始问答；`rejected` = **把答案换成另一个样本的答案**（张冠李戴，明显更差）。
产出 3000 训练对 + 200 留出对。

### 3.2 训练

| 项 | 值 |
| --- | --- |
| 起点 | `out/full_sft_512.pth`（30.03 M，hidden 512） |
| 超参 | β=0.1，lr=5e-7（余弦退火到 5e-8），bs=4，seq=512 |
| 步数 | 750（`epochs=1`） |
| **耗时** | **约 7.5 分钟**（约 1 分钟 / 100 步） |
| loss | 0.2026 → 0.1938 → 0.1368 → 0.0886 → 0.0016 → … → 0.0037（末步 0.2190 是批量噪声） |

### 3.3 效果（200 条留出对）

指标：`margin = 平均对数概率(chosen) − 平均对数概率(rejected)`，逐样本归一化到 token。

| 模型 | 平均 margin | chosen 更优占比 |
| --- | ---: | ---: |
| DPO 前（full_sft） | +0.4366 | 87.5% |
| **DPO 后（dpo）** | **+0.6161** | **93.5%** |

**结论：30M 小模型上 DPO 确实有效**——margin 提升 **+41%**，胜率 +6 个百分点，
成本只有 **7.5 分钟**。这比 SFT（1.8 小时）便宜一个数量级，适合"最后一公里"的风格校正。

> 注意：这是**合成偏好**（答案张冠李戴），衡量的是"回答相关性"这一最粗的偏好；
> 真实业务需要人工标注的偏好对，才能对齐到"有用/无害/诚实"这类细微差别。

## 4. 视频理解（Qwen3-VL-8B 多帧）

从一段乐高机械臂视频抽 4 帧，一次请求送进常驻 vlm-server：

| 项 | 值 |
| --- | ---: |
| 帧数 | 4 |
| 耗时 | **0.99 s** |
| 输出（节选） | "四帧画面展示了一个由乐高积木搭建的机械结构（吊臂部分）在进行周期性的、上下摆动的动作…" |

**结论**：多帧理解的耗时 ≈ 单帧的 2.4 倍（单帧 0.41 s），说明图片编码是主要成本，
而 4 帧的 token 数增加带来的 decode 开销较小。**"抽 4 帧 + 一次提问"约 1 秒**，
比逐帧描述再看文本（4 × 0.41 = 1.6 s + 二次推理）更划算。

## 5. VAD 端点检测（silero-vad）

| 项 | 值 |
| --- | ---: |
| 音频 | 13.75 s |
| 检出语音段 | **4 段** |
| 语音占比 | 82% |
| 耗时 | **155 ms** |
| **速度** | **89× 实时（RTF 0.011）** |

分段结果：`[(0.4, 3.0), (3.5, 5.6), (6.0, 9.9), (10.8, 13.5)]`

**结论**：VAD 便宜到可以"每个音频块都跑"（155 ms 处理 13.75 s）。
把它接在流式 ASR 前面，可以把"固定窗口切分"换成"按语音段触发转写"，
既省算力（静音段不送 ASR）又提高准确率（不会把半个词切断）。

## 6. 第二梯队汇总

| 项目 | 结果 | 关键数字 |
| --- | --- | --- |
| vLLM 多 LoRA | ⚠️ 可用但昂贵 | -42% / -57%；欠训练 adapter 会退化输出 |
| 前缀缓存 | ✅ 强正收益 | 4K 省 49%，16K 省 **89%** |
| DPO（30M） | ✅ 有效 | margin +41%，胜率 87.5%→93.5%，**7.5 分钟** |
| 视频理解（4 帧） | ✅ 可用 | **0.99 s** |
| VAD | ✅ 极便宜 | **89× 实时**（155 ms / 13.75 s） |

**给工程的直接建议：**

1. **LoRA 服务要在 eval 门槛下上线**——欠拟合的 adapter 比没有更糟。
2. **前缀缓存必开**（默认就是开的，别手滑关掉）。
3. **DPO 是性价比最高的对齐手段**（分钟级），前提是有偏好数据。
4. **视频理解走"抽帧 + 单次多图"**，别逐帧全描述。
5. **VAD 前置到 ASR**，按段触发。

# 补充轮：六个闭环实验（2026-11-25）

## 8. LoRA 正式版（400 步 + 留出集评估）

上一轮只训 60 步，只能说明"风格会变"。这次训到 **400 步**，并用**跳开训练集的留出样本**评估。

| 项 | 值 |
| --- | --- |
| 训练步数 | 400（bs 2 × 累积 4 × seq 512） |
| 耗时 | 约 8 分钟（1178–1411 ms/step） |
| 留出集 | 150 条（**跳过文件前 6000 条**，确保不在训练集里） |

| 模型 | eval loss | PPL | 平均答案长度 |
| --- | ---: | ---: | ---: |
| base | 1.7328 | 5.66 | 106.6 字 |
| **lora-400** | **1.4244** | **4.16** | 104.8 字 |

**结论：留出集 loss 降 18%、PPL 降 26%**，说明这不是过拟合训练集的假象。
定性上，LoRA 版把"当然可以，以下是几种更礼貌的表达方式："直接压成"请将文件发给我。"——
风格迁移稳定，且没有牺牲内容。

## 9. VAD + ASR 串联（对比固定窗口）

同一段 13.75 s 音频，两种切分方式后送 faster-whisper-small：

| 方案 | 调用次数 | 耗时 | 与离线整段的字符相似度 |
| --- | ---: | ---: | ---: |
| 固定 2 s 窗口 | 7 | **0.71 s** | 75% |
| **VAD 分段**（4 段） | 4 | 0.86 s | **87%** |

典型错误对比（固定窗口会切断词）：

- 固定窗口：「去管理**程**的一致性」「自**残**保持一致」
- VAD：「**因此保持管理層**的一致性」「自**殘**保持一致」

**结论：VAD 多花 0.15 s，换来 +12 个百分点的准确率**，且调用次数从 7 降到 4（更省算力）。
把 VAD 前置到 ASR 前面是纯赚。

## 10. 32K decode 补齐（上次被 max_model_len 截断）

停掉 vlm-server 后用 `gpu_memory_utilization=0.8`、`max_model_len=40000`：

| 上下文 | TTFT | decode | 每 token 读取 | 有效带宽 |
| ---: | ---: | ---: | ---: | ---: |
| 8,160 | 726 ms | 71.8 tok/s | 4.34 GB | 311 GB/s |
| 16,368 | 1,821 ms | 69.3 tok/s | 5.28 GB | 366 GB/s |
| **32,736** | 5,131 ms | **55.3 tok/s** | 7.15 GB | **395 GB/s** |

**结论：32K 上下文下 decode 只掉 23%（71.8 → 55.3），有效带宽反而升到 395 GB/s（88% 峰值）。**

这修正了"长上下文 decode 会崩"的直觉：KV 读取确实变多（4.34 → 7.15 GB/token），
但带宽利用率也随之提高，两者部分抵消。真正被拖垮的是**prefill**（32K TTFT 5.1 s，是 8K 的 7 倍）。

## 11. ASR 模型尺寸扫描（tiny / base / small / medium）

13.75 s 中文音频，GPU fp16，beam=5：

| 模型 | 加载 | 转写 | 速度 | 文本质量 |
| --- | ---: | ---: | ---: | --- |
| tiny | 0.3 s | 0.26 s | 53.5× | ❌ 管理**稱**、極將、架主、自**殘** |
| base | 0.2 s | 0.22 s | **62.3×** | ❌ 收購**內下**、自**殘** |
| **small** | 0.4 s | 0.34 s | 40.8× | ✅ **全对** |
| medium | 1.3 s | 0.61 s | 22.5× | ✅ 全对（与 small 一致） |

**结论：small 是性价比拐点。**
- tiny/base 更快，但会写错字（"管理层"→"管理稱"），这类错误在字幕/指令场景不可接受
- medium 与 small 输出完全一致，却慢一倍 → **small 是甜点**
- 与前面"13.75 s 音频 GPU 0.39 s（34.9×）"的差异来自 beam 设置与模型（那次是 small + beam 5 的空载测量）

## 12. 视频理解帧数扫描

同一段乐高机械臂视频，2/4/8 帧送 Qwen3-VL-8B：

| 帧数 | 耗时 | prompt token |
| ---: | ---: | ---: |
| 2 | 1.62 s | 542 |
| 4 | 1.41 s | 1,058 |
| 8 | 1.52 s | 2,090 |
| 16（实际只有 8 帧） | 1.37 s | 2,090 |

**结论：2→8 帧，prompt token 涨了 4 倍，端到端耗时几乎不变（1.4–1.6 s）。**

需要注意：这里的绝对值和之前的单帧 0.41 s 不可直接比较（服务刚重启、帧尺寸不同、max_tokens 80 vs 48）。
真正可比的结论是**"多给几帧几乎不要钱"**——图片编码被高效并行，瓶颈在 decode 与调度。

## 13. 多模型共存显存画像

在 vlm-server（6,483 MiB）在线的情况下，逐个加载并记录增量：

| 模型 | 显存增量 |
| --- | ---: |
| vlm-server（Qwen3-VL-8B Q4，基线） | 6,483 MiB |
| + Qwen3-0.6B + LoRA（推理态） | **+1,631 MiB** |
| + faster-whisper-small | **+576 MiB** |
| + SAM2 hiera-tiny | +50 MiB |
| + Depth-Anything-V2-S | +56 MiB |
| **四个模型合计** | **2.26 GiB** |

全卡占用 **54%**（8.8 GB / 16.3 GB），还剩 7.5 GB。

共存状态下的单次延迟：

| 组件 | 延迟 |
| --- | ---: |
| Qwen3-0.6B+LoRA | 433 ms |
| faster-whisper-small | 141 ms |
| SAM2-tiny | 49 ms |
| Depth-Anything | 14 ms |

### 一个必须知道的坑：cu12 与 cu13 不能同进程

| 环境变量 | whisper(CTranslate2, 需 cu12) | SAM2 / Depth（torch cu132） |
| --- | --- | --- |
| 不设 `LD_LIBRARY_PATH` | ❌ `libcublas.so.12 not found` | ✅ 49 ms / 14 ms |
| 设 cu12 库路径 | ✅ 141 ms | ❌ cuDNN 子库加载失败 |

**结论**：`faster-whisper`（依赖 cu12）与 torch cu132 的模型**不能塞进同一个进程**。
正确做法是**分进程/分服务**（各自的 venv），用 HTTP 或 Unix socket 串起来——
这也是为什么生产环境里 ASR 总是一个独立服务。
