# 全优化叠加：单流与高并发是两条不同的最优点

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · vLLM 0.34 · 2026-11-25
> 模型 Qwen3-1.7B（bf16 / GPTQ-Int8）

前面十几轮都是**单项**测：量化多少、CUDA Graph 多少、投机多少。
这一轮把它们**叠起来**，回答一个问题：

> **这台卡上的最优配置到底是什么？**

答案不唯一——**取决于你要延迟还是吞吐**，而且两条路的配置**不一样**。

---

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| 模型 | Qwen3-1.7B（1.7 B 参数） |
| 权重格式 | bf16（3.4 GB）/ GPTQ-Int8（1.7 GB） |
| 引擎 | vLLM 0.34（V1 引擎，FlashInfer 后端，sm120） |
| `max_model_len` | 2048 |
| `gpu_memory_utilization` | 0.78 |
| 输出长度 | 256 token，`ignore_eos=True`（固定长度，排除 EOS 干扰） |
| 采样 | `temperature=0` |
| 统计 | 单流取 3 次中位数，并发取 2 次中位数 |
| KV 容量 | 115,712 token（fp8 KV 下 1808 blocks） |

三种负载分别测，因为**投机解码对负载敏感**：

- **free**：自由生成（"用五句话解释显存带宽"）——通用对话
- **conc32**：32 条并发，每条 256 token——服务吞吐
- **copy**：复述提示里的一段文本——RAG/摘要这类"高重叠"负载

## 2. 叠加矩阵

| # | 配置 | 单流 | 32 并发 | 抄写 | vs eager |
| --- | --- | ---: | ---: | ---: | ---: |
| A | GPTQ-Int8 + eager | 49.8 | 1,489.5 | 48.4 | 1.00× |
| B | GPTQ-Int8 + **CUDA Graph** | 171.9 | 4,159.5 | 171.5 | **3.45×** |
| C | B + **FP8 KV** | 173.8 | **4,408.6** | 173.4 | 3.49× |
| D | C + **ngram 投机** | **238.3** | 2,498.4 | 175.6 | **4.79×** |
| E | bf16 + CUDA Graph | 112.4 | 2,933.8 | 112.3 | 2.26× |
| F | bf16 + Graph + FP8 KV + ngram | 151.6 | 2,507.4 | 162.1 | 3.04× |

（单位 tok/s；"抄写"指 copy 负载的单流速度）

### 2.1 三个层次的收益

| 手段 | 单流收益 | 32 并发收益 | 结论 |
| --- | ---: | ---: | --- |
| CUDA Graph（A→B） | **+245%** | **+179%** | 最大的一根杠杆 |
| 量化 bf16→Int8（E→B） | **+53%** | **+42%** | 稳定 |
| FP8 KV（B→C） | +1% | **+6%** | 只对并发有用 |
| ngram 投机（C→D） | **+37%** | **−43%** ⚠️ | 只对单流有用 |

**FP8 KV 为什么只对并发有用：**
单流 decode 的瓶颈是**读权重**（每 token 要把 1.7 GB 权重读一遍），KV 只有 2K token、几十 MB，
压缩它几乎不影响时间；但 KV 减半让**可用块数翻倍**，32 并发的调度宽松度直接变好（+6%）。

**ngram 为什么在并发下是负收益：** 见下一节，这是本轮最有价值的发现。

---

## 3. ngram 投机的并发交叉点

同一引擎配置（GPTQ + CUDA Graph + FP8 KV），**只开关 ngram**：

| 并发 | 无投机 (tok/s) | +ngram (tok/s) | 比值 |
| ---: | ---: | ---: | ---: |
| 1 | 173.7 | **457.8** | **2.64×** |
| 4 | 685.0 | **1,427.1** | **2.08×** |
| 8 | 1,328.8 | 1,321.7 | **0.99×** ← 交叉点 |
| 16 | 2,467.9 | 1,817.1 | 0.74× |
| 32 | 4,409.0 | 2,058.4 | **0.47×** |
| 64 | 6,578.3 | 2,293.0 | **0.35×** |

### 3.1 机制

- **低并发（1–4）是延迟受限**：一个 batch 只有 1–4 条序列，GPU 的 tensor core 大量空转，
  每步只产出 1 个 token。投机一次草拟 5 个、验证 1 次，等于**用闲置算力换步数** →
  单步能吐 4–5 个 token，收益 2–2.6×。
- **高并发（16+）是吞吐受限**：batch 已经喂饱 GPU，每步产出 = batch_size 个 token。
  投机的验证步要为每条序列单独展开 5 个草稿位置（变长、不规整），
  批处理效率下降；再加上每条序列的 ngram 查表是 CPU 开销 →
  **总吞吐反而掉到 1/3**。

### 3.2 交叉点在 8 并发

这解释了为什么"投机解码能加速"和"投机解码拖慢吞吐"两种说法都有人讲——
**它们说的是不同并发区间**。

### 3.3 收益还取决于负载

两个测试用了不同的 prompt：

| prompt 类型 | 单流收益 |
| --- | ---: |
| 自由生成（"解释显存带宽"） | +37%（173.8→238.3） |
| 高重复（"第 N 问：说明量化影响"） | **+164%**（173.7→457.8） |

ngram 靠**从 prompt 里抄 token** 来草拟，所以：

- 输出与输入重叠越高（RAG 引文、代码补全、摘要、格式化改写）→ 命中率越高
- 开放式创作、推理 → 命中率低，甚至负收益

**一句话：ngram 不是"通用加速器"，是"抄写加速器"。**

## 4. 物理账：为什么量化只拿到 1.53× 而不是 2×

单流 decode 是**纯显存带宽**问题：每生成一个 token，要把全部权重读一遍。

| 项 | bf16 | GPTQ-Int8 |
| --- | ---: | ---: |
| 权重体积 | 3.4 GB | 1.7 GB |
| 实测单流 | 112.4 tok/s | 171.9 tok/s |
| 有效带宽 = tok/s × 权重 | **382 GB/s** | **292 GB/s** |
| 占理论峰值（448 GB/s） | **85%** | **65%** |
| 理论加速 | — | 2.00× |
| 实测加速 | — | **1.53×** |

- **bf16 跑到理论峰值的 85%**——这和我们之前在 `e2e-and-opt.md` 里
  "有效带宽 47%→85%"的结论完全一致 ✅；
- **Int8 只跑到 65%**——反量化（INT8→bf16 的 scale 乘法）多读了一遍数据、多了一遍 kernel，
  所以理论 2× 只兑现成 1.53×。

> 推论：**继续往 4bit 走，收益会进一步打折**（反量化开销占比更大），
> 这与之前"Q4 相对 Q8 只快 20–30%"的观察吻合。

## 5. 两个最优点（可直接抄的配置）

### 5.1 延迟最优：单流 / 低并发（≤4）

```python
LLM(
    model="Qwen3-1.7B-GPTQ-Int8",
    kv_cache_dtype="fp8",
    speculative_config={"method": "ngram", "num_speculative_tokens": 5,
                        "prompt_lookup_max": 8, "prompt_lookup_min": 3},
    # 不要 enforce_eager
)
```

| 指标 | 值 |
| --- | ---: |
| 单流 | **238 tok/s**（自由生成）/ **458 tok/s**（高重叠） |
| 相对 eager | **4.8×**（自由生成）/ 9.2×（高重叠） |
| 32 并发 | 2,498 tok/s（**别用这个配置跑服务**） |

### 5.2 吞吐最优：高并发服务（≥8）

```python
LLM(
    model="Qwen3-1.7B-GPTQ-Int8",
    kv_cache_dtype="fp8",
    # 不加 speculative_config
)
```

| 并发 | 吞吐 |
| ---: | ---: |
| 8 | 1,329 tok/s |
| 32 | **4,409 tok/s** |
| 64 | **6,578 tok/s** |

### 5.3 一张表决策

| 场景 | 并发 | 开 ngram？ |
| --- | ---: | --- |
| 语音助手 / 单用户 agent / 边缘设备 | 1–4 | ✅ 开 |
| 小团队内部服务 | 8 | ⚠️ 持平，随便 |
| 批量推理 / API 服务 | ≥16 | ❌ **一定关** |

## 7. 结论

1. **CUDA Graph 仍是最大杠杆**（+245% 单流），任何配置都不该开 `enforce_eager`；
2. **量化第二**（+53%），但受反量化开销拖累，理论 2× 只兑现 1.53×；
3. **FP8 KV 是"并发专用"优化**（单流 +1%，32 并发 +6%），成本几乎为零，建议默认开；
4. **ngram 投机是"低并发专用"优化**，交叉点在 **8 并发**，
   超过就掉到 1/3 吞吐——**别在服务端开**；
5. **最优配置不是一个点，是两条线**：
   - 延迟线：GPTQ + Graph + FP8 KV + ngram → **238 tok/s**
   - 吞吐线：GPTQ + Graph + FP8 KV → **6,578 tok/s @ 64 并发**
