# 回归基准：把 29 篇文档的结论变成可验证检查

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-26
> 代码：`bench/`（`run.py` + `manifest.json` + `README.md`）

前面 29 篇文档都是**一次性实验**：数字写下来了，但没人验证过它还能不能复现。
这一轮把它们变成**可执行资产**：

> **9 项检查，快检查 1 分钟、全检查 4 分钟，退出码可直接接 CI。**

## 2. 为什么是这 9 项

它们覆盖了**四类最容易被环境破坏的结论**：

| 类别 | 检查 | 被什么破坏 |
| --- | --- | --- |
| **物理上限** | `kv_bytes_per_token`、`decode_roofline_1p7b`、`concurrency_32k` | 换模型/换卡/改公式 |
| **投机公式** | `spec_break_even` | 接受率或成本比变化 |
| **硬件** | `gpu_bandwidth` | 换卡、驱动、电源策略 |
| **检索** | `rag_r1` | 换嵌入、重建索引、改切片 |
| **模型行为** | `json_compliance`、`needle_8k` | 量化、引擎、chat 模板 |
| **文档本身** | `docs_indexed` | 新加文档忘了更新 README |

### 2.1 三类检查的成本差异

| 类型 | 代表 | 耗时 | 何时跑 |
| --- | --- | ---: | --- |
| 纯数学 | `kv_bytes_per_token` | <0.1 s | 每次改文档 |
| 单模型 | `json_compliance` | ~8 s | 每次改代码 |
| 多模型/大上下文 | `needle_8k` | ~13 s | 发布前 |

## 3. 设计上的四个决定

### 3.1 期望值放在 JSON，不放代码

`manifest.json` 里每一项都带 `why`：

```json
"spec_break_even": {
  "expect": 1.0, "tol": 0.06, "unit": "x",
  "why": "(1+5*0.349)/(1+5*0.35)，实测接受率 34.9% ≈ 成本比 35%"
}
```

改预期不用改代码，也能让人看懂"这个数字从哪来"。

### 3.2 两种判据

| 判据 | 用法 | 例子 |
| --- | --- | --- |
| `expect` + `tol` | 公式/物理量 | KV 字节数、并发路数 |
| `min` | 有噪声的行为指标 | R@1 ≥ 67%、JSON ≥ 90% |

**不能给模型类指标设死值**——它们是概率性的，容差必须诚实。

### 3.3 快慢分离

默认只跑"不加载模型"的检查（1 分钟内），慢检查用 `--include-slow` 显式开启。
否则每次改文档都要等 4 分钟，没人会跑。

### 3.4 失败要能定位

每项都输出**实测值、期望值、一句细节**：

```
rag_r1   0.75   ≥0.67   PASS   (9/12 题 top-1 命中, 10.7s)
```

看到 `9/12` 就知道是检索问题，不用再去翻日志。

## 4. 建这套东西时踩的两个坑（都值得记）

### 4.1 指标名和实际算的东西不一致

第一版 `rag_r1` 里写的是：

```python
top = [...][:5]
hit += any(expect in f for f in top)   # 这是 R@5
```

名字叫 R@1，算的是 R@5，于是显示 **91.7%**，和文档里的 75% 对不上。
查了逐题位置才确认：**评测代码没写错参数，是名字和实现对不上**。

改成 `expect in top[0]` 后回到 75%，与文档一致。

> 这正是 `MANUAL.md` 第 9 章说的：**判据错一半来自代码，不来自模型。**

### 4.2 `--only` 被 `--include-slow` 过滤掉

第一版过滤器写的是：

```python
if (not want or n in want) and (args.include_slow or not v["slow"])
```

用户明确 `--only rag_r1` 时，仍然被 `slow` 条件拦住，结果"全部 0 项通过"。
显式指定应该覆盖默认过滤：

```python
if (n in want if want else (args.include_slow or not v["slow"]))
```

> 教训：**"通过 0 项"和"通过全部"一样危险**，运行器必须把"筛出来 0 项"当成错误。

（这条已经可以加进运行器：`if not names: 报错退出`。）

## 5. 怎么加一项新检查

三步：

```python
# 1) run.py 里加函数
@check("my_check", slow=False)
def _mine():
    value = ...            # 算出来
    return value, "一句话细节"

# 2) manifest.json 里加期望
"my_check": {"min": 0.8, "unit": "...", "why": "为什么是这个值"}

# 3) 跑一下
python run.py --only my_check
```

约束：**检查函数只返回 (数值, 细节)**，不要自己打印结论——
统一的表格输出才能比较、才能接 CI。

---

## 6. 这套东西的价值

| 没有它 | 有它 |
| --- | --- |
| 换了驱动，不知道结论还成不成立 | 一条命令 4 分钟验证 |
| 新同事要读 29 篇才知道基线 | 跑一遍看到 9 个数字 |
| 文档里的数字没人敢信 | 每个数字都有对应检查 |
| 改切片/换嵌入后悄悄退化 | R@1 低于 67% 直接 FAIL |

> 它不提高性能，但它让前面 29 篇从"实验记录"变成"可验证的资产"。

---

## 7. 局限

1. **只覆盖 9 个结论**，29 篇里还有大量数字没进检查（如各类吞吐、TTS 质量）；
2. **模型类检查有噪声**：R@1 单项 ±8 pp、JSON 10 题粒度 10 pp；
3. **依赖本机资源**：bge-m3、reranker、rag 索引、1.7B 权重缺一不可；
4. **不是性能基准**：它验证"结论是否成立"，不是"跑分多少"。

---

## 8. 结论

1. **物理类结论最适合做成检查**：公式简单、零成本、任何机器可验；
2. **模型类检查必须给容差**，且要报分母（`9/12` 比 `75%` 有用）；
3. **建检查的过程本身就在抓 bug**：本轮就抓出"R@5 冒充 R@1"和"`--only` 失效"两个；
4. **"通过 0 项"要当错误处理**——否则 CI 会在你最需要它的时候骗你。
