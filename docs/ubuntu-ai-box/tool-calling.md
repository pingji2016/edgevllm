# 工具调用实测：模型没问题，是判据错了

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-26
> Qwen3-1.7B · 10 个工具 × 60 条指令 · 三种模式

这是文档里第一次碰**工具调用（function calling）**——"agent" 的基础能力。

结果最有意思的不是模型，而是**评测**：

> 严格判据下完整准确率 **66.7%**，
> 换成**按字段类型的等价判据**后是 **96.7%**（58/60）。
> **18 条"失败"全是判据误杀**，真错只有 2 条。

---

## 1. 实验设置

| 项 | 值 |
| --- | --- |
| 模型 | Qwen3-1.7B（bf16，`enable_thinking=False`） |
| 工具 | 10 个：天气/计算器/搜索/日历/邮件/数据库/翻译/单位换算/提醒/读文件 |
| 指令 | 60 条，每个工具 6 条（模板句 + 随机实体） |
| 判据 | 工具名精确匹配；参数按"关键字段"比对 |
| 模式 | `free`（自然语言要求 JSON）、`xgr`（xgrammar 强制 schema）、`name_only`（只输出工具名） |

Schema（`xgr` 模式用）：

```json
{"type":"object",
 "properties":{"tool":{"enum":[10 个工具名]},
               "arguments":{"type":"object"}},
 "required":["tool","arguments"]}
```

---

## 2. 三种模式的原始结果

| 模式 | JSON 合法 | 工具选对 | 参数（严格） | 完整（严格） | 延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `free` | **100%** | **98.3%** | 66.7% | 66.7% | 747 ms |
| `xgr` | 100% | 98.3% | 66.7% | 66.7% | 735 ms |
| `name_only` | — | **95.0%** | — | 95.0% | **315 ms** |

### 2.1 三个反直觉

1. **JSON 本来就 100% 合法**——不约束也全对，`xgrammar` 一分没加；
2. **工具选择几乎不是问题**：98.3%（59/60）；
3. **只输出工具名反而更差**（95% vs 98.3%）——见 §5。

---

## 3. 重新评分：66.7% → 96.7%

把 60 条的预测逐条拉出来看，20 条"失败"里 **19 条是等价写法**：

| 类型 | 金标 | 模型输出 |
| --- | --- | --- |
| 语言用代码 | `中文` | `zh` |
| | `英文` | `en` |
| | `西班牙语` | `es` |
| 单位用英文 | `小时 / 分钟` | `hour / minute` |
| | `千克 / 磅` | `kg / lb` |
| | `毫升 / 升` | `milliliter / liter` |
| 表达式加空格引号 | `city=北京` | `city = '北京'` |
| 列名同义 | `stock=0` | `inventory = 0` |
| 中文错误 → 英文 | `错误` | `error` |
| 时间写法 | `明天 08:00` | `明天早上 8 点` |
| | `今晚 22:00` | `今晚十点` |
| | `下午 15:00` | `下午三点` |
| 联系人解析 | `张三` | `zhangsan@example.com` |

按字段类型做等价判据（语言码/单位别名/表达式归一/时间转 24 小时制/自由文本包含）后：

| 判据 | 完整准确率 |
| --- | ---: |
| 严格（原始） | **40/60 = 66.7%** |
| **等价（按字段类型）** | **58/60 = 96.7%** |
| 其中需人工确认（邮箱补全） | 2 条 |
| **真错** | **2 条** |

**18 条被严格判据误杀——接近 30 个百分点。**

### 3.1 两条真错

| 指令 | 金标 | 预测 | 问题 |
| --- | --- | --- | --- |
| 今晚八点建一个健身提醒，60 分钟 | `create_calendar_event` | `set_reminder` | **工具选错**（"提醒"这个词有歧义） |
| 给老板发邮件说明延期原因 | `subject="延期原因"` | `subject="关于延期的说明"` | 编造了主题（还补了一个邮箱） |

### 3.2 两条"需要人工确认"

模型把 `张三 → zhangsan@example.com`、`团队 → team@example.com`。
在真实系统里这可能是对的（需要查通讯录），但也可能是**编造**。
这类必须由业务逻辑兜底，不能算模型对。

---

## 4. 为什么 `xgrammar` 这次没用

因为它解决的是"**格式违规**"，而这次格式本来就 100% 合法。

对照之前 `inference-acceleration.md` 里的一次实验：
同样用 xgrammar，**约束前 0/4、约束后 4/4**。差别在哪？

| 条件 | 这次工具调用 | 之前那次 |
| --- | --- | --- |
| schema | 一层：`{tool: enum, arguments: object}` | 多层/严格字段 |
| 模型 | 1.7B | 更小/更弱 |
| 结果 | 本来就合法 | 0/4 违规 |

**结论：约束解码是"保险"，不是"加速器"。**
格式本来没问题时，它只带来编译开销和每 token 的 bitmask 计算（本次 747 → 735 ms，基本持平）。

> 什么时候该上约束：**schema 复杂、字段多、模型小**。
> 什么时候不用：**简单 schema + 1.7B 以上**。

---

## 5. 为什么"只输出工具名"反而更差

`name_only` 模式：95.0%，比 JSON 模式的 98.3% 低 3.3 pp。

两个可能的原因：

1. **少了 JSON 这个"脚手架"**：写 `{"tool": ` 的过程本身让模型先锁定"我在选工具"；
2. **解析更脆**：只输出名字时，模型偶尔带前后缀（"工具：get_weather"），
   解析规则要额外兜底。

> 实用建议：**不要为了省 token 去掉 JSON 外壳**——它对小模型是有效的格式锚点。

---

## 6. 可落地的四条

| # | 建议 | 依据 |
| ---: | --- | --- |
| 1 | **schema 里给 enum**（语言、单位、工具名） | 模型不用猜 `zh` 还是 `中文`，省掉一整类歧义 |
| 2 | **判据按字段类型写**，不要字符串精确匹配 | 严格判据把 96.7% 测成 66.7% |
| 3 | **联系人/文件路径这类外部实体，不要信任模型补全** | 2 条编造邮箱 |
| 4 | **约束解码按需开**，简单 schema 不必 | 本次零收益 |

## 8. 结论

1. **1.7B 的工具选择已经很可靠**（98.3%），参数也基本正确（等价判据 96.7%）；
2. **"参数只有 66.7%"是判据错误**：语言码、单位别名、时间写法、空格引号都被当成错；
3. **约束解码在这里零收益**——格式本来就合法；它是保险，不是加速器；
4. **真错只有 2 条**：一条工具歧义（提醒 vs 日历），一条编造主题；
5. **评测方法论又赢了一次**：这已经是第三次（千分位、批量解码、现在是字段等价）
   因为判据把 30 pp 的差距"测没了"。
