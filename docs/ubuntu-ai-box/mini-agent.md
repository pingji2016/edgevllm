# mini agent：单轮工具选对 98%，多轮却只有 65%

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-27
> Qwen3-1.7B · 6 个真实执行工具 · 20 个多步任务

承接 `tool-calling.md`：单轮工具选择 **98.3%**。这一轮问的是更实际的问题：

> **让模型连续调用工具（读文件 → 计算 → 写文件），它还能保持吗？**

答案：

> **无工具直接答 20%，用工具 65%。** 工具把成功率翻了 3 倍，
> 但**失败几乎全在"计划"和"接地"**，不在"选工具"。

---

## 1. 设置

### 1.1 工具（全部真实执行）

| 工具 | 作用 | 沙箱 |
| --- | --- | --- |
| `read_file(path)` | 读文件 | 仅 `/tmp/agent_ws` |
| `write_file(path, content)` | 写文件 | 同上 |
| `list_dir(path)` | 列目录 | 同上 |
| `calc(expression)` | 安全算术（AST 白名单） | — |
| `search_docs(query)` | BM25 检索本地 32 篇文档 | — |
| `now()` | 当前时间 | — |

### 1.2 循环

```
模型输出 {"tool": ..., "arguments": ...}
      ↓ 程序执行
<observation> 结果 </observation>
      ↓ 回填对话
下一轮（最多 6 步）
      ↓
{"tool":"finish","arguments":{"answer":...}}
```

### 1.3 任务

20 个需要 2–3 步依赖的任务，覆盖四类：

- **读 → 算**：「读 sales.csv，revenue 求和」
- **算 → 写**：「算 37*18，写入 math.txt」
- **检索 → 答**：「在文档里搜 KV cache 每 token 占多少 KB」
- **列目录 → 比较**：「哪个文件名最长」

对照：同一批任务**不给工具**直接回答。

## 2. 结果

| 方式 | 成功 | 平均步数（成功任务） |
| --- | ---: | ---: |
| 无工具直接答 | **4/20 = 20%** | — |
| **mini agent** | **13/20 = 65%** | 2–4 步 |
| 原始判据（有 bug） | 10/20 = 50% | — |

> 原始判据把 3 条正确结果判成错（KV 112 被要求 116、`37*18` 取了第一个数字 37、`data.csv` 金标算成 110）。
> **修正判据后 50% → 65%**——这已经是本项目第四次遇到"判据吃掉真实水平"。

## 3. 失败的 7 条，分五类

| 类型 | 数量 | 具体案例 |
| --- | ---: | --- |
| **不读就答 / 跳步** | 2 | 「log.txt 里 ERROR 几次」→ 去搜文档，直接答 0；<br>「dates.txt 最早日期」→ 搜文档后答 **2026-11-25**（文档里的日期） |
| **表达式构造错** | 1 | 求平均 → 写成 `10+20+30/3` = 40（应为 20） |
| **路径幻觉且不纠错** | 1 | 连续 6 次尝试 `workzone/words.txt`，从不改路径 |
| **输出格式违规** | 1 | 一步里吐了两个 JSON 对象 → 解析失败 |
| **推理缺失** | 1 | 列了目录，但没比较文件名长度，直接答 `words.txt` |
| 题目歧义 | 1 | 「bge-m3 的 R@1」→ 答 42%（那是 bge-small 的数） |

### 3.1 一个典型的好例子

```
任务：计算 37*18，写入 math.txt 并回答结果
→ calc("37*18")        <observation>666</observation>
→ write_file("math.txt","666")  <observation>已写入 3 字符</observation>
→ finish(answer="666")  ✅
```

### 3.2 一个典型的坏例子

```
任务：log.txt 里 ERROR 出现了几次
→ search_docs("ERROR log")     ← 应该 read_file
   <observation>[MANUAL.md] L = −log σ(...)</observation>
→ finish(answer="0")           ← 没读文件就下结论
```

**模型不是"不会用工具"，是"没想清楚该用哪个、什么时候该停下核实"。**

## 4. 三个可复用的判断

### 4.1 工具能救"不知道"，救不了"不认真"

| 任务类型 | 无工具 | 有工具 |
| --- | ---: | ---: |
| 需要读文件里的具体值 | ~0% | **高**（读对了就对） |
| 需要多步计算 | 低 | 中（表达式容易写错） |
| 需要比较/推理 | 低 | 低（工具帮不上） |

### 4.2 多轮的瓶颈是"计划"，不是"选择"

单轮选择 98.3%，多轮成功率 65%。差距来自三件事：

1. **该调工具时没调**（跳步直接答）；
2. **调错了不回头**（路径错了连续重试）；
3. **拿到观察不会用**（格式违规、表达式错）。

> 如果要提升，优先做**流程约束**（强制"先读后答"、失败重试上限、每步校验），
> 而不是继续优化"选工具"的准确率。

### 4.3 小模型 agent 的实用形态

| 做法 | 效果 |
| --- | --- |
| 给明确的工具 schema + 枚举 | 单轮 98%（已验证） |
| **每步做结果校验**（如"文件存在？数字合法？"） | 能拦住大部分幻觉 |
| **限制步数 + 强制收敛** | 防死循环（本例有 1 次超步数） |
| 关键实体不让模型补全（路径/收件人） | `workzone/` 这类幻觉 |

---

## 6. 结论

1. **工具让 1.7B 的成功率从 20% 提到 65%**（3.25×）；
2. **失败不在"选工具"**（单轮 98.3%），在**跳步、路径幻觉、表达式错、格式违规、不比较**；
3. **改判据又救回 15 pp**（50% → 65%）——第四次证明"判据比模型更容易出错"；
4. **小模型 agent 的关键是流程约束**：先读后答、每步校验、限制步数。
