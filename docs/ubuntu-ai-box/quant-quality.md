# 量化对任务准确率的影响：Int8 无损，4bit 掉 6.7 pp

> 机器 `pingji-MS-7B89` · RTX 5060 Ti 16 GB · 2026-11-26
> 模型 Qwen3-1.7B · 三个任务 · 300 题配对检验

之前所有量化实验测的都是 **PPL**（困惑度）。PPL 涨一点看起来无害，
但它和**任务准确率**不是一回事。

这一轮直接测准确率：

> **GPTQ-Int8 完全无损（52% vs 50%，在噪声内），而且快 1.53×；
> NF4 掉 6.7 pp，配对检验显著（z=3.02）。**

---

## 1. 实验设置

### 1.1 三个任务（都不是 PPL）

| 任务 | 规模 | 判据 |
| --- | ---: | --- |
| **A 算术** | 100 / 300 题，三位数 × 两位数 | 答案逐字正确 |
| **B 指令** | 10 题，抽取姓名/年龄/城市转 JSON | `json.loads` 成功且 ≥3 个键 |
| **C 长上下文** | 8K needle，2 深度 × 2 种子 | 输出含暗号 `741928` |

### 1.2 两个配对（同引擎对比，避免引擎差异）

| 对比 | 引擎 | 说明 |
| --- | --- | --- |
| **bf16 vs GPTQ-Int8** | vLLM 0.34 | 同一套采样参数 |
| **bf16 vs NF4** | HF transformers 5.2 + bitsandbytes 0.50 | NF4 只能在 HF 里跑（vLLM 0.34 不支持 bnb） |

> ⚠️ 跨引擎的数字不可直接比（vLLM 与 HF 的注意力实现不同），
> 所以每组只在**组内**比较。

---

## 2. 结果

### 2.1 vLLM：bf16 vs GPTQ-Int8

| 模型 | 算术（100） | JSON（10） | needle（4） |
| --- | ---: | ---: | ---: |
| bf16 | 50.0% | 100% | 3/4 |
| **GPTQ-Int8** | **52.0%** | 100% | 3/4 |

**Int8 没有掉点**（+2 pp 在 100 题的 ±5 pp 噪声内），
而昨天的速度实测是 **171.9 vs 112.4 tok/s（1.53×）**。

### 2.2 HF：bf16 vs NF4

| 模型 | 算术（100） | JSON（10） | needle（4） | 峰值显存 |
| --- | ---: | ---: | ---: | ---: |
| bf16 | 49.0% | 100% | 3/4 | 6.53 GB |
| **NF4** | **38.0%** | 100% | 3/4 | **4.58 GB** |

### 2.3 300 题配对检验（确认不是噪声）

| | 数值 |
| --- | ---: |
| bf16 准确率 | **49.0%** |
| NF4 准确率 | **42.3%** |
| 差距 | **−6.7 pp** |
| 两者都对 | 115 |
| 两者都错 | 141 |
| **只有 bf16 对** | **32** |
| **只有 NF4 对** | 12 |
| McNemar z | **3.02**（p < 0.01，显著） |

> 100 题时测出 −11 pp，300 题配对后收敛到 **−6.7 pp**。
> 这说明**小样本会放大效应**，配对检验才是可靠的判据。

---

## 3. 三个发现

### 3.1 Int8 是"免费"的

| 维度 | bf16 → Int8 |
| --- | --- |
| 准确率 | 50% → 52%（噪声内） |
| 速度（单流） | 112.4 → **171.9 tok/s（1.53×）** |
| 权重大小 | 3.4 GB → 1.7 GB |

**没有任何理由不用 Int8**——除了极少数对数值极其敏感的场景。

原因：Int8 每层权重有 256 个量化级，相对误差约 0.4%，
对 1.7B 这种"每层贡献都不大"的模型几乎不改变输出分布。

### 3.2 4bit 的损失是**任务选择性**的

| 任务 | NF4 影响 |
| --- | --- |
| 算术（精确计算） | **−6.7 pp（显著）** |
| JSON 格式 | 0（都是 100%） |
| 8K 检索 | 0（都是 3/4） |

**量化伤的是"精细数值"，不是"格式"或"检索"。**

- JSON 任务考的是**结构**，16 个量化级足够；
- needle 任务考的是**位置**，只要注意力还在就不受影响；
- 算术要求把两个三位数相乘的中间结果**逐位对齐**，权重上 0.5% 的扰动
  就足以让最后一位翻车。

### 3.3 显存的账没有想象中划算

| | bf16 | NF4 | 节省 |
| --- | ---: | ---: | ---: |
| 权重（1.7B） | 3.4 GB | 0.9 GB | 2.5 GB |
| **峰值显存（batch 8）** | 6.53 GB | 4.58 GB | **仅 1.95 GB** |

因为峰值里还有 **activations + 6400×词表 logits**，这部分不随权重量化而减小。
在 16 GB 卡上，4bit 省下的 2 GB 通常**换不来一个更大的模型**，却要付 6.7 pp 的准确率。

## 4. 选型建议

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 16 GB 卡跑 1.7B | **GPTQ-Int8** | 无损 + 1.53× 提速 |
| 显存紧张（如 8 GB 卡跑 7B） | NF4 | 唯一能塞进去的选项 |
| 数学 / 代码 / 精确抽取 | **不要 4bit** | 实测 −6.7 pp |
| 分类 / 格式转换 / 摘要 | 4bit 可接受 | 这类任务对量化不敏感 |

### 4.1 一个经验法则

> **任务越依赖"逐位精确"，量化越危险。**
> 格式、分类、检索 → 4bit 没问题；
> 算术、代码补全、数值抽取 → 至少 Int8。

### 5.1 局限

- 只测了 Qwen3-1.7B 一个模型、一种 4bit 配置（NF4 + double quant）；
- JSON（10 题）和 needle（4 题）样本太小，只能说明"没有巨大退化"，不能排除小幅差异。

---

## 6. 结论

1. **Int8 是无损加速**：准确率在噪声内，速度 1.53×，应当默认使用；
2. **NF4 掉 6.7 pp 是真实的**（z=3.02），而且 100 题时会误测成 11 pp——
   **量化评估必须做配对检验**；
3. **量化损伤是任务选择性的**：算术/精确计算最敏感，格式与检索几乎不受影响；
4. **4bit 省 2 GB 显存，代价是精度**：在 16 GB 卡上通常不值得，
   除非你的任务是"格式/分类"这类不敏感场景。
