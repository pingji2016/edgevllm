## 第 1 章：显存带宽 —— 为什么卡“算得快但吐得慢”

### 🎯 一句话

**生成每个字，都要把整个模型从显存里搬一遍。所以速度上限 = 搬运速度 ÷ 模型大小。**

### 🧠 直觉

想象你在图书馆查资料：

- **算力** = 你翻书的速度（每秒能读多少页）；
- **带宽** = 管理员从书库跑到你桌子的速度（每秒能搬多少书）。

生成第一个字时，模型要**把所有参数都读一遍**（相当于把整座书库搬一次），
但真正“算”的部分很少。所以你不是被“算得慢”卡住，是被“搬得慢”卡住。

一个具体数字：1.7B 模型（bf16）有 3.4 GB 参数，
你的卡带宽 448 GB/s → 理论上 **每秒最多 131 个字**。实测 112，达到 85%。

> 这就是为什么"换更快的内存"比"换更强的算力"更能提升单条响应速度。

### 📐 唯一的公式

```
每秒字数上限 = 带宽(GB/s) ÷ 模型大小(GB)
```

| 模型 | 大小 | 理论上限 |
| --- | ---: | ---: |
| 0.6B bf16 | 1.2 GB | 373 字/秒 |
| 1.7B bf16 | 3.4 GB | 131 字/秒 |
| 1.7B Int8 | 1.7 GB | 263 字/秒 |
| 8B bf16 | 16 GB | 28 字/秒 |

### 🔬 3 分钟实验

```python
# 测你这张卡的真实带宽（约 20 秒）
import torch, time
x = torch.empty(1<<28, dtype=torch.uint8, device="cuda")   # 256 MB
y = torch.empty_like(x)
for _ in range(3): y.copy_(x)
torch.cuda.synchronize(); t = time.time()
for _ in range(20): y.copy_(x)
torch.cuda.synchronize()
print(f"{2*x.numel()*20/1e9/(time.time()-t):.0f} GB/s")
```

预期输出：**350–420 GB/s**（标称 448）。

然后验证公式：`112.4 × 3.4 = 382 GB/s` → 和实测带宽的 85–90% 吻合。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “算力越强越快” | 单条对话受带宽限制，算力几乎闲置 |
| “量化一半，速度翻倍” | 实测 1.53×，因为反量化也要时间（见第 5 章） |
| “batch 大了单条更快” | batch 提高**总吞吐**，单条反而略慢 |

### ✅ 自测

<details><summary>为什么 8B 模型在你卡上单流大概只有 28 字/秒？</summary>

16 GB 权重 ÷ 448 GB/s ≈ 0.036 秒/字 → 28 字/秒。
而且 16 GB 权重几乎占满显存，剩下的空间不够放 KV cache，实际更难跑。
</details>

## 第 2 章：KV cache —— 模型为什么要“记笔记”

### 🎯 一句话

**模型每读一个新字，都要回看前面所有字；把前面算过的中间结果存下来，就是 KV cache。**

### 🧠 直觉

读一篇文章时，你会在旁边做笔记（"前面说过 X"）。
不做笔记，每读一句都要重读全文，慢得没法用。

模型也一样：它每生成一个字，都要"注意"前面所有字。
如果不缓存，第 1000 个字要重算前 999 个——所以必须缓存成"笔记"。

代价：**笔记要占地方，而且随文章长度线性增长。**

### 📐 唯一的公式

```
每个字的笔记大小 = 2 × 层数 × KV头数 × 头维度 × 字节数
```

Qwen3-1.7B：28 层、8 个 KV 头、每头 128 维、bf16（2 字节）

```
2 × 28 × 8 × 128 × 2 = 114,688 B ≈ 112 KB
```

| 上下文长度 | 笔记占用 |
| ---: | ---: |
| 4K 字 | 0.46 GB |
| 8K 字 | 0.92 GB |
| 16K 字 | 1.84 GB |
| 32K 字 | **3.67 GB** |

### 🔬 3 分钟实验

用 vLLM 起服务时故意开大上下文，看它自己报的数字：

```bash
# 起服务（日志里会打印 KV 容量）
python -m vllm.entrypoints.openai.api_server \
  --model <你的模型> --max-model-len 32768 --gpu-memory-utilization 0.8
```

日志里会出现：

```
GPU KV cache size: 74,752 tokens
Maximum concurrency for 33,280 tokens per request: 2.25x
```

这就是"最多同时服务 2 个人"的意思。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “模型说支持 32K，就能服务 32K” | 能"看"，但同时只能服务 2 个请求 |
| “上下文越长越好” | 长上下文和并发是**抢同一块显存** |
| “KV cache 是磁盘缓存” | 它在显存里，断电就没 |

### ✅ 自测

<details><summary>16 GB 卡、1.7B 模型，想同时服务 8 个人，每人上下文最多多长？</summary>

可用 KV ≈ 12.4（总预算）− 3.4（权重）− 1.5（临时）≈ 7.5 GB。
7.5 GB ÷ 8 人 ≈ 0.94 GB/人；0.94 GB ÷ 112 KB ≈ **8,400 字**。
所以每人 8K 上下文是上限。
</details>

## 第 3 章：批处理 —— 为什么服务端要“拼单”

### 🎯 一句话

**一条请求时 GPU 大部分在空转；把多条请求拼在一起算，总吞吐能翻几十倍。**

### 🧠 直觉

一辆大巴能坐 50 人。只坐 1 个人也照样烧油——这就是单条请求的 GPU。
**批处理 = 拼车**：多个人一起走，每人的成本就降下来了。

注意两件事：

- **总吞吐**（所有人加起来每秒多少字）会大涨；
- **单条延迟**（某个人多久到站）基本不变，甚至略慢。

### 📐 唯一的公式

```
总吞吐 ≈ 单条速度 × 并发数 × 效率系数
```

实测（1.7B，Int8）：

| 并发 | 总吞吐 | 单条 |
| ---: | ---: | ---: |
| 1 | 173 字/秒 | 173 |
| 8 | 1,329 | 166 |
| 32 | 4,409 | 138 |
| 64 | 6,578 | 103 |

并发 64 时，总吞吐是单条的 **38 倍**，但每条从 173 降到 103。

### 🔬 3 分钟实验

用同一句话，分别发 1 条和 32 条，比较总耗时：

```python
# 伪代码：vLLM 离线接口
llm.generate([prompt] * 1)
llm.generate([prompt] * 32)   # 看总时间是不是只比 1 条多一点
```

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “并发高就快” | 单条会变慢，是**吞吐**变高 |
| “并发越高越好” | 显存会被 KV 吃满，64 路已经接近上限 |
| “批处理=排队” | 引擎是**动态插队**的，新请求随到随算 |

### ✅ 自测

<details><summary>为什么给 100 个用户做批量总结，比一个个跑快得多？</summary>

因为单条时 GPU 空转，批处理把空转填满。100 条的总耗时可能只比 1 条多几倍，而不是 100 倍。
</details>

## 第 4 章：CUDA Graph —— 为什么“少发指令”能快 3 倍

### 🎯 一句话

**GPU 干活很快，但“派活”很慢。把几百次派活录下来重放，就能省掉大半时间。**

### 🧠 直觉

你去餐厅点 290 道菜，如果每道菜单独叫一次服务员，光叫人就累死了。
CUDA Graph 相当于**一次把整桌菜报完，厨房按固定流程走**。

小模型单步只要 8.9 毫秒，但每步要发 **~290 条指令**，每条 25 微秒 →
**7.25 毫秒都在“叫人”**。

### 📐 唯一的公式

```
单步时间 = 计算时间 + 指令数 × 每条指令开销
```

- 普通模式：8.9 + 7.25 ≈ 16.3 ms → 61 字/秒
- Graph 模式：8.9 + ~0 → **112 字/秒**

### 🔬 3 分钟实验

```bash
# 同一个模型，只改一个参数
python stack_all.py     # 内部对比 A_eager 与 B_graph
```

看输出：`A_eager 49.8` vs `B_graph 171.9`（Int8 模型）。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “Graph 会改变输出” | 实测逐字一致 |
| “大模型用不上” | 大模型也有 20–40% 提升 |
| “并发高时更明显” | 反过来，高并发时收益只有 10–25% |

### ✅ 自测

<details><summary>为什么 CUDA Graph 对小模型效果最明显？</summary>

因为小模型计算本身很快（8.9 ms），"派活"的 7.25 ms 占了近一半；
大模型计算要几百毫秒，同样的派活开销就微不足道了。
</details>

## 第 5 章：量化 —— 用更少的位数存权重

### 🎯 一句话

**把每个参数从 16 位压缩到 8 位或 4 位，省显存也省搬运时间，代价是精度。**

### 🧠 直觉

照片压缩：JPEG 把 24 位颜色降到更少的信息，肉眼看不出，但放大到像素级就有差别。

- **8 位**：还有 256 个档位，误差约 0.4% → 几乎无损；
- **4 位**：只有 16 个档位，误差 1–2% → 算术会翻末位。

### 📐 唯一的公式

```
量化误差 ≈ (最大值 − 最小值) / 档位数
```

8 位：`1/256 ≈ 0.4%`；4 位：`1/16 ≈ 6%`（实际经过分块缩放会好一些，约 1–2%）。

### 🔬 3 分钟实验

```bash
python quant_paired.py    # 300 题，bf16 vs 4bit 逐题配对
```

看输出：

```
bf16: 147/300 = 49.0%
NF4 : 127/300 = 42.3%
只有 bf16 对 32 | 只有 NF4 对 12
```

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “4bit 一定更差” | 对格式/分类几乎无损，只伤"逐位精确" |
| “量化省一半显存就能放大一倍的模型” | 临时数据和输出层不缩，实际只省 30% |
| “PPL 没涨就没事” | PPL 和任务准确率不是一回事 |

### ✅ 自测

<details><summary>为什么 4bit 对 JSON 输出没影响，对算术有影响？</summary>

JSON 考"结构"（是或不是某个字段），分类式判断对 1% 扰动不敏感；
算术要求末位精确（相对误差 1e-4），1% 的权重量化误差足以翻末位。
</details>

## 第 6 章：投机解码 —— 先猜后验

### 🎯 一句话

**让便宜的方式先猜几个字，再用大模型一次性验货；猜对了就赚，猜错了就退。**

### 🧠 直觉

实习生先写 5 版方案，老板一次性审批：

- 老板审批 5 个方案的成本 ≈ 审批 1 个（并行）；
- 如果实习生猜得准，一次就过 5 个 → 赚 5 倍；
- 如果猜不准，被否掉，白干。

### 📐 唯一的公式

```
加速比 ≈ (1 + k×a) / (1 + k×c)
```

- `k` = 每次猜几个（草稿长度）
- `a` = 猜对的比例（接受率）
- `c` = 草稿的成本 ÷ 大模型的成本

**赚钱条件：`a > c`。** 猜得再准，如果草稿本身很贵，也是白搭。

### 🔬 3 分钟实验

```bash
python draft_spec.py    # 0.6B 给 1.7B 当草稿
```

看输出：

```
1 并发: 112.4 → 101.7 (0.90x)
接受率 34.9%，草稿成本比 ≈ 35%
```

`0.349 ≈ 0.35` → 正好卡在平衡点，所以白干。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “投机一定能加速” | 只有 `a > c` 时才行 |
| “并发越高越赚” | 8 并发以上一律亏（验证步拆散批处理） |
| “草稿模型越小越好” | 太小则猜不准，`a` 下降 |

### ✅ 自测

<details><summary>为什么 ngram 投机在“抄写”任务上能到 2.6 倍，在自由创作上不行？</summary>

ngram 是从**输入里抄**片段当草稿。抄写任务（复述、改写、代码补全）输入输出高度重叠，
`a` 很高且 `c≈0`；自由创作时输入里没有可抄的，`a` 极低。
</details>

## 第 7 章：长上下文 —— 为什么 32K 会崩

### 🎯 一句话

**上下文每翻倍，注意力计算涨 4 倍（平方），显存涨 2 倍（线性），而训练长度是个悬崖。**

### 🧠 直觉

两个人开会，1 对 1 交流很简单；
10 个人开会，人人都要和人人说话，复杂度是 `10×10`；
30 个人开会，就失控了。

模型里，每个字都要和其他所有字"互相注意"，所以是**平方增长**。

### 📐 唯一的公式

```
注意力计算量占比 ≈ 6.75e-5 × 上下文长度
```

| 上下文 | 注意力占比 |
| ---: | ---: |
| 8K | 35% |
| 32K | **69%** |

### 🔬 3 分钟实验

```bash
python needle.py    # 在长文中藏一句话，看模型能不能找到
```

实测：

| 长度 | 8K | 16K | 32K |
| --- | ---: | ---: | ---: |
| 找到率 | 100% | 78% | **11%** |

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “标称 32K 就能用 32K” | 训练长度的边缘就是能力悬崖 |
| “找不到会说不知道” | 它会**抓一个旁边的数字**，答得很自信 |
| “上下文越长越省事，不用检索” | 32K 的失败率是 89%，而且静默 |

### ✅ 自测

<details><summary>为什么 32K 时"把整篇文档塞进去"不如"检索后塞 4K"？</summary>

32K 命中率 11%、prefill 5 秒、只能 2 路并发；检索方案 R@1 75%、prefill 0.3 秒、能 20+ 路并发。
准确率、延迟、并发全面占优。
</details>

## 第 8 章：RAG —— 让模型“查资料”

### 🎯 一句话

**把文档切块、变成向量、按问题找最像的几块，再让模型看着这几块回答。**

### 🧠 直觉

开卷考试：

1. **切块** = 把书拆成一页页（太小丢上下文，太大塞不进）；
2. **向量** = 给每页贴一个"内容指纹"，指纹相近 = 内容相近；
3. **检索** = 拿问题的指纹去找最像的几页；
4. **重排** = 把找到的页**逐字读一遍**，重新排序（更准，但更慢）；
5. **回答** = 只看这几页作答。

### 📐 唯一的公式

```
最终召回 = 向量找得广（top-20） → 重排找得准（top-3）
```

| 阶段 | 作用 | 实测 R@1 |
| --- | --- | ---: |
| 向量（小模型） | 粗筛 | 42% |
| 向量（大模型） | 粗筛更好 | 58% |
| + 重排 | 精排 | **75%** |

### 🔬 3 分钟实验

```bash
python hybrid_rag2.py    # 12 个问题的五路消融
```

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “加了 BM25 一定更好” | 实测 +0（强嵌入模型下是冗余的） |
| “切得越细越准” | 表格行脱离表头就失去意义 |
| “检索对了答案就对” | 小模型会抄错数字，要让它指位置 |

### ✅ 自测

<details><summary>为什么切片时要给每一行拼上"章节标题 + 表头"？</summary>

`| Q4_K_M | 221.8 |` 这一行没有主语、没有列名，脱离表头就不知道 221.8 是什么。
拼上标题/表头后，定位准确率从 4/12 提到 6/12。
</details>

## 第 9 章：训练 —— SFT / RL / 蒸馏到底在干什么

### 🎯 一句话

**SFT 是抄答案，RL 是做题打分自己摸，蒸馏是跟着老师学。**

### 🧠 直觉

| 方法 | 类比 | 什么时候用 |
| --- | --- | --- |
| **SFT** | 老师给标准答案，你照着抄 | 模型完全不会 |
| **DPO** | 给你看"好答案 vs 坏答案"，自己体会 | 想让回答更讨喜 |
| **RL** | 只给分数，自己试错 | 模型会一点，想更准 |
| **蒸馏** | 跟着学霸做题，学他的解法 | 想把大模型能力搬给小模型 |

### 📐 唯一的公式

```
梯度 = p − 1
```

`p` 是模型给正确答案的概率。

**这句话解释了三件事：**

1. `p` 接近 1（已经会了）→ 梯度接近 0 → **训练等于复习**（这就是 "只喂正确答案" 的 RFT 无效的原因）；
2. RL 的负分会让**错误答案的 p 下降**，所以有效；
3. 没有约束（KL）时，`p` 会全压到一个众数上 → **塌缩**。

### 🔬 3 分钟实验

```bash
python grpo_math.py --steps 50    # 亲眼看着熵掉到 0
```

会看到：`组内正确率 0%`、`格式 0%`、模型最后只会输出同一个数。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “只喂正确答案就能学会” | 正确答案的 `p` 本来就高，梯度≈0 |
| “RL 一定比 SFT 强” | 起点 0% 时 RL 只会塌缩 |
| “蒸馏能传全部能力” | 只传"大概对"，精度传不过去 |
| “loss 降到 0 是好事” | 说明没有梯度了，模型在背书 |

### ✅ 自测

<details><summary>为什么 0.6B 蒸馏后 98% 的答案误差<1%，但只有 46% 完全正确？</summary>

它学会了数量级和前几位（这些在教师数据里重复出现），
但最后一位是细粒度决策，需要容量去表示；0.6B 装不下这个边界。
</details>

## 第 10 章：怎么判断一个提升是不是真的

### 🎯 一句话

**小样本会骗人；比较两个模型必须"同一批题、同一种解码、配对检验"。**

### 🧠 直觉

抛硬币 10 次出现 7 次正面，不代表硬币有问题。
样本越小，噪声越大。

### 📐 唯一的公式

```
误差范围 ≈ ±1.96 × √(p(1−p)/n)
```

| 题量 | 50% 准确率的 95% 区间 |
| ---: | ---: |
| 100 | ±9.8 pp |
| 200 | ±6.9 pp |
| 300 | ±5.7 pp |

**所以"提升 2 pp"在 100 题上基本是噪声。**

### 🔬 3 分钟实验

同一模型、同一批题，用两种方式跑（批量 / 逐条）：

- 批量解码：50.5%
- 逐条解码：47.0%

**什么都没改，差了 3.5 pp。** 所以对比必须固定解码方式。

### ⚠️ 常见误解

| 误解 | 实际 |
| --- | --- |
| “准确率涨了就是有效” | 先看样本量和置信区间 |
| “题目越多越好” | 题目**分布**比数量更重要（要均衡） |
| “模型说找不到就是失败” | 有时是判据写错了（千分位、多个正确版本） |

### ✅ 自测

<details><summary>你在 100 道题上把准确率从 47% 提到 49%，能说"有效"吗？</summary>

不能。100 题的 95% 区间约 ±10 pp，2 pp 完全在噪声内。
至少 300 题 + 同一批题的配对检验（McNemar）才能下结论。
</details>

## 附录 C：常见误解 10 条（背下来少走弯路）

1. **“算力越强越快”** → 单条对话受带宽限制。
2. **“量化一半速度翻倍”** → 实测 1.53×。
3. **“支持 32K 就能用 32K”** → 训练长度是悬崖，16K 才安全。
4. **“上下文长就不用检索”** → 32K 失败率 89%，且静默。
5. **“4bit 一定更差”** → 只伤逐位精确，格式/检索无损。
6. **“投机一定加速”** → 必须 `接受率 > 草稿成本比`。
7. **“多采样投票总能提分”** → 错误系统性时反而更低。
8. **“loss 降到 0 是好事”** → 没梯度了，在背书。
9. **“准确率涨了就是有效”** → 先看样本量和配对检验。
10. **“混合检索是标配”** → 强嵌入下实测 +0。

## 最后一个建议

学这些东西，**不要背结论，要记"预测"**。

每学一个概念，问自己一句：

> **“如果这个原理是对的，我应该能测到一个什么数字？”**

- 懂带宽 → 能预测"1.7B 最多 131 字/秒"；
- 懂 KV → 能预测"32K 只能 2 路"；
- 懂量化 → 能预测"4bit 会让末位翻车"；
- 懂梯度 → 能预测"只喂正确答案没用"。

**能预测，就是懂了。** 预测错了，正好是你下一个该补的地方。
