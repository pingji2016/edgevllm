## 0. 一句话结论

K3 是「**同构融合**」而不是「CPU + 加速器」：8 个通用核 **X100** 和 8 个 AI 核 **A100**
共享同一套 RISC-V ISA（RVA23）、跑**同一个 Linux**，靠 **IME 矩阵扩展 + 1024-bit 向量**
把 AI 算力做在 CPU 流水线里，而不是外挂 NPU。

- 对外宣传的 **60 TOPS 是 INT4 稀疏峰值**；稠密 INT4 30、稠密 INT8 15、FP16/BF16 7.5 TOPS。
- 设计约束是 **12 nm、die < 150 mm²、TDP 30 W** —— 所有取舍都是在这三个数下做的。
- 默认调度**不让普通程序上 A100**：X100（CPU 0–7）跑系统与通用负载，A100（CPU 8–15）
  只接显式绑定过去的 AI/1024-bit 向量任务。

## 1. 它想解决什么问题

边缘设备进入「本地大模型 + 机器人」阶段后，同时要两件事：

1. **通用性能**：控制面、系统服务、复杂应用逻辑要跑得动、跑得稳；
2. **AI 吞吐**：推理要快，而且要能随模型变大继续扩展。

传统做法是「host CPU + 加速器」的异构：两套 ISA、两套工具链、两套运行时，
很多情况下等于在同一个盒子里跑**两个高度重复的 Linux 栈**。代价是：

- 资源重复（内存、存储、常驻服务）；
- 跨边界开销（IPC、数据拷贝、上下文切换）；
- 维护成本（两份内核/用户态组件的版本、安全补丁、验证矩阵）。

K3 的选择是在**一颗芯片内把两者统一到同一 ISA / 同一 OS**，
把「异构税」压到可管理范围。白皮书把这条路线类比为手机时代的 big.LITTLE：
既要高性能又要低功耗，但**只跑一个操作系统**。

> 注意「同构」指的是 **ISA 和 OS 统一**，不是「两类核完全等价」。
> X100 和 A100 在微架构、向量宽度、是否支持 Hypervisor 上差别很大，
> 所以调度上仍然是**非对称**的（见 §6）。

## 2. 硬指标与设计约束

| 约束 | 取值 | 理由（原文） |
| --- | --- | --- |
| 工艺 | **12 nm 级 FinFET** | 12FFC+ 已长期量产、成本与供应风险低；N12e 面向 AIoT/边缘 |
| 面积 | **die < 150 mm²** | die 成本随面积超线性增长、良率随面积下降；避免超大封装/高层基板 |
| 功耗 | **TDP 30 W** | 对齐边缘 AI/机器人模块的主流功耗档（原文举例 Jetson AGX Orin 的 15/30/50 W 档） |

| 组件 | 规模 | 目标 |
| --- | --- | --- |
| **X100** | 8 核，2 簇 | 通用计算；RVA23 全合规；控制面确定性、生态兼容、长期可维护 |
| **A100** | 8 核，2 簇 | AI 推理主力；60 TOPS 级 AI 算力 |
| **RT24 实时核** | 双核（基于开源 CVA6） | 电机控制、传感等实时任务；MSI 快速唤醒、压低抖动 |

## 3. 系统组成与几个外围子系统

### 3.1 APIC / MSI

- **APLIC** 遵循 RISC-V Advanced Interrupt Architecture（AIA）；**ACLINT** 遵循
  RISC-V ACLINT 规范。
- **MSI** 把外部中断变成「设备向指定地址写一条消息」，避免传统引脚中断的
  **共享 IRQ 线**和扫描多个 handler 的开销；消息的顺序语义还能省掉「中断先到、
  数据还没可见」时的额外同步/回读。
- MSI 支持多向量、可定向到指定核：机器人场景下可以把关键传感器/控制环的中断
  钉到隔离核上，降低抖动。
- X100/A100 的 M-mode 与 S-mode 都支持 MSI 中断 ID **1–511**；X100 在
  VS-mode 下支持 **1–63** 直通给虚拟机；A100 没有 Hypervisor 扩展，不能做 VM 直通。

### 3.2 Trace

X100/A100 的指令追踪符合 RISC-V Hart-to-Trace Interface；编码器按 **N-Trace 1.0**
（Nexus-based）设计，寄存器定义兼容 RISC-V Trace Control Interface 1.0，支持：

- BTM 模式输出；
- Debug Trigger 控制 trace 开关与事件；
- 地址压缩编码；
- Trace 数据溢出时的事件传输。

> 处理器追踪到底在记什么、BTM 是什么、普通开发为什么用不到，见 [§12.2](#122-n-trace-与处理器追踪)。

### 3.3 T100 IOMMU

遵循 RISC-V IOMMU 架构规范与 RISC-V Server SoC 规范，硬件提供：

- 设备 DMA 的地址翻译、访问控制、隔离保护；
- 硬件辅助 I/O 虚拟化：**PCIe passthrough**、**SR-IOV**。

## 4. X100：通用核

X100 以 **OpenC910**（玄铁 C910 的开源版本）为起点，做了大范围改造。
目标：**4-wide 发射、乱序执行**，在能效和 die 面积之间平衡，
面向高性能边缘负载，也能进入门级服务器。

关键原则：**不引入任何私有 ISA 扩展**，只用 RISC-V 标准指令集；
完整实现 RVA23 的必选部分，并实现部分可选扩展。

### 4.1 前端：把取指带宽和分支预测补上

4-wide 发射首先卡在前端供指。X100 的改动集中在两条线：**分支预测准确率**和**取指并行度**。

| 改动 | 内容 | 目的 |
| --- | --- | --- |
| L0 BTB | 优化时序路径、适度扩容、换更适合分支局部性的替换算法 | 提高 L0 BTB 命中率，减少取指气泡 |
| 条件分支方向 | **TAGE**（Tagged Geometric History Length）替换 Bi-Mode | 用长全局历史预测复杂控制流 |
| 返回地址 | 链表式 **RAS** | 乱序/深嵌套调用下更稳的返回预测 |
| ICache 组织 | 2-way → **4-way** set-associative | 降低 way 冲突导致的缺失 |
| ICache↔L2 带宽 | 128 bit → **256 bit/cycle** | 降低访问通道争用 |
| 发射宽度 | 3 → **4 条/cycle** | 喂满后端乱序执行 |
| 指令融合 | 前端集成多种静态指令融合模式 | 不新增 ISA 的前提下提高有效发射带宽 |
| 可靠性 | ICache **奇偶校验** + RERI 上报 | ICache 不会有脏行，奇偶校验即可实时发现单比特错 |

### 4.2 中核：3-wide → 4-wide 的连带改造

ID（解码）阶段从 3-wide 改成 4-wide；下游必须一起加宽，否则结构冒险会把收益吃掉：

- **Issue Queue 加深**，容纳更多在途指令；
- **增加一个 ALU**，但**不新增寄存器堆读端口** —— 复用 BRU 的读端口：
  没有分支指令发射时，两个整数发射队列可以借 BRU 的端口把指令发给新 ALU。
  这样既提高并行度，又不让关键时序路径变长。
- **立即数操作数消除**：某些立即数不再分配物理寄存器，缓解寄存器堆压力；
- **Early Wake-Up**：长延迟操作（除法、L1 miss）提前释放依赖资源；
- **误预测时更早释放前端资源**；
- **Issue Queue 管理**：调整平衡策略 + 提前释放，等效于增加队列深度。

### 4.3 存储子系统：带宽、延迟、冒险

| 方向 | 做法 |
| --- | --- |
| 执行带宽 | 两条通用流水线各带独立 load/store；DCache 访问带宽翻倍 |
| 冒险 | **snoop monitor** 过滤伪冒险 + **uop 粒度冒险预测器**，冲突指令延后执行 |
| 总线 | 256-bit，CHI-like 协议接多核互连 |
| 缓冲 | 重设 WMB；LFB 与 VB 合并为 **FVB**（资源共享，减少总开销、提高利用率） |
| 延迟 | L1 miss/L2 hit 的 early wake-up；AMO 不拆分原子执行（降低 AMO 延迟与活锁） |
| 预取 | **SPP**（Stream-based Page Prefetching）+ 总线负载反馈动态调预取距离 |
| 虚拟化 | 支持 H 扩展；TLB 缓存中间页表项，降低多级页表遍历开销 |
| 可靠性 | DCache **ECC** + Poison 上报 + RERI；可选延迟上报或立即返回错误信号 |

### 4.4 向量单元（RVV 1.0）

- **VLEN = 256 bit，ELEN = 64 bit**；支持 INT8–INT64、FP16/BF16–FP64；
- 独立向量流水线：**2 条算术 + 2 条 load/store**，每条约 128-bit，可并发；
- **解耦设计**：向量指令在主流水线完成解码和标量操作数重命名后，
  进入独立的向量指令缓冲，再拆分/发射/执行 —— 便于物理布局与 floorplan；
- 每周期最多并发 **2 条访存 + 2 条计算**；每条发射端口按 128-bit 粒度处理，
  即 **LMUL=1 的一条指令拆成两个 128-bit uop**；
- 选择双 128-bit 而不是单 256-bit 数据通路，是为了在不同向量算子之间
  更细粒度地分配资源（例如复杂 permute 只有一条 128-bit 执行单元）；
- **地址生成与数据处理解耦**：地址阶段由主流水线的 LSU 做，数据阶段由向量单元做，
  两者用 instruction ID 协调；LSU 不用等向量寄存器依赖解决就能发起访存；
- 段访问等复杂模式用**专用 transpose buffer** 加速重排。

### 4.5 多核互连

- 缓存策略从 **inclusive 改为 exclusive**，配合每核的 cache tag backup
  精确跟踪多核环境下的 cache line 状态；通过消除 cache 层级间冗余拷贝
  提高可用容量（1:1.5 的扩容比例用于减少 back-invalidation 频率）。
- **提前访问 L2**：检测到地址冲突时取消流水操作；L1 miss/L2 hit 的
  **load-to-use 延迟可低至 17 cycles**，返回数据直接送核，绕过访问事务队列。
- 预取：**next-line**（按指令和页表遍历缺失训练）+ **best-offset**
  （按数据访问模式训练）组合，兼顾空间局部性与复杂 stride。
- **4 个 cache bank 并行访问**；内部总线 256-bit。
- 一致性协议：bypass 优化把常见 snoop 事务延迟降 **4 cycles**；
  支持 **self-snooping**（解决核内 cache aliasing）；
  **precise bank snooping**（省功耗）；事务队列状态机重设计，缩短常见事务生命周期。
- 高并发锁：引入 **CleanUnique** 事务类型，避免重负载下的活锁。
- RAS：RERI 标准错误上报 + poison 机制 + 总线数据检查；
  可在「RERI 延迟上报」与「传统即时错误信号」之间灵活选择。

## 5. A100：为 Transformer 做的 AI-CPU

A100 是**原生 AI 计算**的 RISC-V AI-CPU，靠 **SpacemiT-IME** 指令集扩展实现。
它**完整支持 RVA23 通用 CPU 功能（但不含 Hypervisor 扩展）**，
因此大模型推理和普通 AI 应用仍在**标准的 RISC-V 统一编程模型**里。

设计沿三条轴展开：

| 维度 | 做法 |
| --- | --- |
| 集成（System） | AI 单元作为**紧耦合协处理器嵌进 CPU 流水线**，单 ISA 模型，降低驱动开销、上下文切换和「异构税」 |
| 计算（Computation） | 面向 Transformer，向量化微架构 + 低精度/混合精度，提高算子并行度与能效 |
| 数据流（Memory/Datapath） | 以带宽为中心：软件管理的 local memory + 访存/执行解耦（异步 DMA 预取，重叠搬运与计算） |

> 原文对簇内组成的表述是「每簇 4 个 scalar core、2 个 vector core、2 个 local-memory
> bank、1 个共享 L2；两个 vector core 共享 1 个 Tensor Core 和 1 个 local-memory bank」。
> 对上层来说，一个 A100 cluster 等价于 **4 个 A100 Linux 线程**；
> 两个 cluster 就是 8 个线程，这也是运行时调度的基本单位。
> （原文这句的「core」混用了标量/向量执行资源，别按 4+2=6 去理解核数。）

### 5.1 向量单元

- 两条并行向量流水线：负责拆分、依赖处理、向量寄存器读写；结果主要在 **VE3–VE5** 产生；
- 算子按「指令类型 + 数据通路特征」分五类：**INT、FP、CRYPTO、FDV、IME-1.0**；
- 寄存器堆 **VLEN = 1024 bit**，32 个架构向量寄存器 `v0–v31`；
  一条向量指令一次可处理最多 1024 bit 数据；
- 资源分配原则：高频、吞吐关键的算子（加减/比较/位操作/窄宽 MAC）优先映射到
  可双发射的宽执行资源，并尽量在 VE3/VE4 出结果；稀有宽度的算子用跨 lane 合并
  或多周期时分复用，避免为峰值宽度过度配置；
- 复杂/低频算子（permute、部分宽通路、迭代除法）**故意限制发射带宽和通路宽度**，
  换面积与能效。
- 12 nm 上做 VLEN=1024 的时序收敛很难：寄存器堆读写端口、bypass/选择网络要做
  结构划分和分级流水，关键路径靠 retiming 和 fanout 控制压缩；后端靠 floorplan、
  关键块摆放、约束驱动把长互连和拥塞的影响压下去。最终在 **2.1 GHz** 收敛。

### 5.2 IME 与 Tensor Core

SpaceMiT-IME 提供**两级矩阵乘累加**能力（IME 1.0 与 2.0 的定位差别见 [§12.4](#124-ime-10-与-ime-20)）：

| 单元 | 归属 | 执行宽度 | 支持矩阵乘 | 目标 |
| --- | --- | --- | --- | --- |
| **IME 1.0** | 每核私有 | 256-bit | INT8×INT8→INT32，如 A(4×8)·B(8×4) | 复用向量单元低吞吐通路，做小矩阵 MAC |
| **IME 2.0 (INT)** | **双核共享** | 1024-bit | INT4：8×32 / 32×8；INT8：8×16 / 16×8 | 专用高吞吐通路 |
| **IME 2.0 (FP)** | **双核共享** | 1024-bit | FP16/BF16：8×8；FP8→BF16 | 混合精度矩阵乘 |

Tensor Core 由两个核共享，每个核每周期可提交一条 **MMA** 指令；操作数与结果都在
向量寄存器里。向量子系统有 32 个向量寄存器、每个 **128 B**（合计 4 KB），
每核有独立的 **512-bit load 通道**；前端支持每周期「1 条 512-bit load + 1 条 MMA」
双发射。

**为什么要算 operational intensity**：共享 MAC 的峰值是 1 MAC/cycle，
单核能不能喂饱它，取决于每次从内存搬一个字节能做多少次 MAC。

- 单条 MMA（M=N=8, K=16）：一次 1024 次 MAC；A 是 8×16 INT8 = 128 B，需要 2 个 load 周期；
  **利用率 U = 1/2 = 50%**，**ρ = 1024/128 = 8 MAC/B**。
- 分块 + 寄存器 blocking（16 个向量寄存器放 C-tile，α×β 个 tile 同时累加，
  α+β ≤ 8）：最优在 **(α, β) = (2, 4)**，**ρ ≈ 10.67 MAC/B**，
  load 12 周期 / MAC 8 周期，**U = 8/12 ≈ 66.7%**。
- **双核共享 MAC**：两个核并行加载并持续提交 MMA，才能把共享 MAC 拉到 **100% 饱和**；
  单核即使 operational intensity 做到 10.67，产生 MAC 请求的速率仍可能低于
  共享单元的服务速率，导致又贵又费面积的 MAC 资源闲置。

> 这段是白皮书里最有「工程味」的地方：**峰值 TOPS 不是单核跑出来的，要靠双核配合喂饱共享单元**。
> 这也解释了为什么软件栈以「4 线程一个 cluster」为调度单位，而不是单核。

### 5.3 存储：local memory 与主存

两条访问路径分开优化：

- **Local memory**：服务计算密集、数据复用强的阶段（向量/矩阵核心算子），
  目标是把 working set 尽量留在近核存储里，稳定供数、减少 stall；
- **主存**：服务访存密集阶段（参数读取、cache 更新，尤其是 decode 的流式访问），
  目标是从主存稳定拿到持续读带宽，并有足够的延迟隐藏能力。

**local memory 容量怎么定**：不是把单一指标优化到极致，而是在面积、功耗、
带宽开销等多目标下取 Pareto 折中，还受频率上限、macro 摆放和互连布线约束。
白皮书用 CNN/LLM/ViT 多类负载做性能-成本建模和参数扫描找 knee point，
最终选 **Qwen-30B-A3B** 作为工程参考，优先覆盖 **30B–80B 规模模型推理**的
working set 驻留需求。

**主存设计用 Little's Law**：稳态下 `带宽 = 在途并发数 / 平均服务延迟`。
所以优化方向是两条：提高可维持的在途请求数（覆盖 DRAM 延迟、减少带宽气泡），
降低或摊销有效延迟（减少冲突和排队）。A100 cluster 级的在途窗口约 **100**，
采用**非对称共享**：单核不设固定静态配额，负载需要时可以借用超过均分的窗口。

### 5.4 1024-bit 向量带来的实际好处

32 × 1024 bit = **4 KB** 的架构寄存器，相当于一个超快 scratchpad：

- **Norm-style broadcast**（`C = A[..., C] * Scale[C]`，C 常为 128/256/512/768）：
  C < 512 时 16 个向量寄存器就装得下 Scale，主循环里只需全局加载一次；
- **FlashAttention**：hidden dim 常为 128/64，FP16 下 2 个向量寄存器就能装一个
  sequence chunk 的 hidden；不用 tensor 扩展，光 RVV 就能消掉 hidden 维内循环，
  把 Q·K 累加常驻在 2–4 个向量寄存器里，累加阶段基本不依赖 L1/L2；
- **减少 VPR spill**：LMUL=4/8 的代码（尤其 exp/tanh 近似）容易向量寄存器溢出；
  VLEN=1024 时用 **LMUL=1** 就能达到 VLEN=256 + LMUL=4 的计算宽度，
  大幅降低溢出概率，kernel 更稳。

## 6. RVA23、虚拟化与新特性

### 6.1 RVA23 与 Hypervisor

- 上一代 K1 的 X60 核完整符合 **RVA22**；K3 的 X100 完整实现 **RVA23U64**（用户态）
  与 **RVA23S64**（监督态）的全部必选扩展，并主动支持可选扩展：
  向量加密（Zvkng、Zvksg、Zvbc）与 FP16/BF16（Zfh、Zvfh、Zfbfmin、Zvfbfmin、Zvfbfwma）。
- RVA23 的意义是给 64-bit 应用处理器一个**统一的 ISA 基线**：
  二进制生态有保证，同时用少量可发现的可选扩展保留灵活性。
- **X100 支持 H 扩展，每个物理核最多 7 个活跃 VM**。
  A100 **不实现 H 扩展**，因为 AI 负载只调度到 A100、A100 不承担 hypervisor 管理职责。
- 虚拟化的两阶段地址翻译有额外开销，X100 的 TLB 做了三层缓解：
  1. ITLB/DTLB 直接缓存 **GVA→SPA**，L1 TLB 命中时虚拟化不增加翻译延迟；
  2. L2 TLB 同时缓存 GVA→SPA 和 **GPA→SPA**，扩大覆盖；
  3. PTW 缓存非叶子页表项（GVA→GPA），guest TLB miss 时加速页表遍历。

> 页表、TLB、GVA→GPA→SPA 两阶段翻译的完整解释见 [§12.3](#123-页表tlb-与虚拟化的两阶段翻译)。

### 6.2 向量加密

X100 和 A100 都实现 Vector Crypto，覆盖国际算法（AES、SHA-2）与中国商用密码
（SM4、SM3）。ISA 设计强调**数据无关的执行延迟**，提高抗时序侧信道能力；
支持 Zvkn/Zvks 等套件。实现策略统一：**SM3 与 SHA2-64 用 256-bit 元素组，
其余指令用 128-bit 元素组**。

### 6.3 低精度与 FP8

- X100/A100 都完整兼容 RVA23 的 FP16/BF16 可选子集：
  Zfh、Zvfh（标量/向量 FP16），Zfbfmin、Zvfbfmin、Zvfbfwma（BF16 与 BF16 矩阵操作）。
- **A100 额外集成 FP8（E4M3/E5M2）向量转换指令**，转换直接进执行流水线，
  把 FP8→FP16/BF16 的转换延迟降低数量级。
- 设计 K3 时 RISC-V 还没有官方 OFP8 扩展；白皮书说标准化后会迁移到官方扩展。
- FP8 的价值不只是「转得快」：模型不同层/算子对数值敏感度不同，混合精度下
  可以**按需动态切换精度**，只在必要时用高精度存储，降低片外带宽需求 ——
  这对带宽受限的 AI 加速很关键。

## 7. 软件栈与调度

### 7.1 一个 Linux，但调度是分区策略

- X100 与 A100 同源但角色不同：X100 主打通用，VLEN=256；
  A100 主打 AI/高吞吐向量，VLEN=1024、无 H 扩展。
- 16 个核由 Linux 作为 **SMP** 管理，OS 暴露统一的 16 核逻辑视图；
  但调度策略**显式分区**：
  - **X100 = CPU 0–7**：默认域，跑系统与通用负载；
  - **A100 = CPU 8–15**：AI 专用域，只接特定 AI 算法与向量密集任务；
  - 用户线程创建时默认绑到 X100；**X100 饱和也不迁移到 A100**；
  - 需要 A100 的任务（AI 推理、1024-bit 向量算法）必须在线程创建后**显式绑定**；
    一旦绑定，整个生命周期只能在 A100 上跑，不能迁回 X100。
- 这样做的**底线收益**是避免 ISA 不匹配：只有通用指令的线程如果被调度到
  只支持部分 AI 指令的 A100 上，会触发异常。
- 白皮书自己也承认代价：
  1. **负载不均**：可能 A100 闲着、X100 跑满；
  2. **跨核迁移受限**：不同 VLEN 的向量上下文不能乱迁，调度器更复杂；
  3. **生态不友好**：依赖修改 Linux 内核，难以上游；应用开发者还得懂硬件感知调度。
- 改进方向：用 **Linux cpuset** 把「策略执行」从内核改到用户态 ——
  X100（CPU0–7）为默认域，A100（CPU8–15）为 AI 专属域；只有应用显式标记为
  AI 任务才允许放进 AI 域。用 Linux 原生的资源隔离框架，降低系统复杂度。

> 这段和我们板子上的实测完全对得上：
> `/proc/set_ai_thread` + `taskset -c 8-15` 就是这套「显式绑定」的落地；
> 通用 LLM 绑上去反而慢 4~6 倍，原因是通用 kernel 按 VLEN=256 编译/调优。
> 详见 [`k3-hardware/a100-cores.md`](k3-hardware/a100-cores.md)。

### 7.2 AI 软件栈

形态：**ONNX Runtime + 私有后端** 的推理引擎，加上**基于 tile 的 Triton 算子编译器**，
两者共享同一套 runtime、线程与内存优化策略。

- **统一 API 算子库**：手写 kernel 起步，算子 API 对齐 **MLIR meta-op** 定义，
  保证语义完整与跨框架兼容；同时暴露 C API 给早期 AI 编译器调用 ——
  这样在完整 IR 代码生成就绪之前，就能把整条编译流水线跑起来。
- **X100 runtime**：推理引擎和 Triton 都以 **A100 cluster 为硬件调度单位**，
  等价于一组 4 个 A100 Linux 线程；两个 cluster 就是两组共 8 个线程，
  概念上类似 **CUDA multi-stream**。X100 上的 runtime 把 tile 级任务
  动态派发到当前负载最轻的 A100 线程组。
- 后续设计会支持**分布式推理**：runtime 变成拓扑感知，按局部最优调度 tile 任务，
  在保持透明编程模型的同时提高推理引擎的可扩展性。
- 演进路径很务实：先用**手写 kernel** 把私有场景的性能打满，再引入**编译器生成**
  把收益泛化。

### 8.2 向量加密：OpenSSL

归一化到标量实现（标量 = 1），越大越好：

| 算法 | 16 B | 256 B | 16384 B |
| --- | ---: | ---: | ---: |
| chacha20 | 0.5 | 1.1 | 2.1 |
| sha256 | 1.8 | 3.8 | **10.5** |
| sha512 | 1.4 | 1.7 | 2.3 |
| SM3 | 1.5 | 2.1 | 2.6 |
| aes-128-cbc | 4.7 | 12 | **13.9** |
| aes-256-cbc | 4.8 | 12.1 | **13.7** |
| SM4 | 3.5 | 5.9 | 6.2 |
| GHASH | 2.5 | 21.3 | **46.6** |
| hmac(sha256) | 1.9 | 3.2 | 10.2 |

解读：

- AES/SHA/SM3/SM4/GHASH 有专用加速指令，相对标量和「通用向量化」都是数量级收益；
  AES 的专用查表指令消除了传统查表带来的 cache 访问开销；
- GHASH 的 `vghsh` 深度流水，每轮只要 **3 cycles**，大消息下到标量基线的 **46.6×**；
- ChaCha20 以移位和模加为主，向量加速潜力有限，只有 `vror` 等少量指令能帮上忙，
  消息足够大（> 64 KB）时向量并行的收益才摊得回来。

> 白皮书正文 §3.3.2 说「典型加解密 kernel 最高可达 60×」，但 Table 6 实测最高是
> **GHASH 46.6×**。引用时以表为准，60× 当作正文的概括性说法。

## 10. 读的时候要留意的点

1. **这是 Preview 版**：References 还是 TBD，带宽部分明确说「系统级优化仍在进行中，
   结果不代表最终峰值」。所有数字按「厂商预览」看待。
2. **60 TOPS 的口径**：INT4 **稀疏**。稠密 INT4 30、稠密 INT8 15、FP16/BF16 7.5。
   和 NPU 标称值比较时先对齐「稠密/稀疏、INT4/INT8、是否含稀疏加速」。
3. **「同构融合」≠ 两类核等价**：ISA 和 OS 统一，但调度是分区的，
   A100 默认不接通用负载，且没有 Hypervisor 扩展。白皮书自己也列了三条代价
   （负载不均、迁移复杂、内核改动难上游）。
4. **单核跑不出峰值**：共享 Tensor Core/MAC 要双核持续提交才能饱和；
   CNN 数据也显示 4 线程、batch=2 才有明显提升。
5. **评测频率与板子不同**：2.4/2.1 GHz vs 板上的 2.15/1.8 GHz，且板子可能受
   供电/散热/固件限制。跨平台比分数时先归一化频率。
6. **表格抽取有歧义**：Table 1（AI 算力）、Table 7（读带宽单位）、Table 8（CNN 行序/单位）
   都是从双栏 PDF 文本还原的；关键引用建议回原文核对。
7. **正文与表格的 60× vs 46.6×**：以 Table 6 为准。
8. **FP8 是自定义指令**：设计时 RISC-V 尚无 OFP8 标准，未来会迁移；
   现在写 FP8 kernel 要注意这是厂商私有路径。

## 11. 术语速查

| 术语 | 含义 |
| --- | --- |
| ISA | Instruction Set Architecture，指令集架构：软件与硬件之间的契约（指令、寄存器、数据类型、特权级）。x86-64 / ARMv9 / RISC-V 都是 ISA |
| RVA23 | RISC-V 64-bit 应用处理器 Profile，规定必选/可选扩展基线 |
| RVV | RISC-V Vector Extension，向量扩展；VLEN 是向量寄存器位宽 |
| TLB | Translation Lookaside Buffer，MMU 里缓存「虚拟地址→物理地址」翻译结果的小缓存。**它不是页表**，页表在内存里，TLB 只是最近翻译结果的 cache |
| 页表 / page walk | OS 维护的多级地址映射表；TLB 未命中时由硬件走多级页表查地址，这次查表叫 page walk |
| GVA / GPA / SPA | guest 虚拟地址 / guest 物理地址（guest 以为的物理地址）/ 系统物理地址（真实 DRAM）。虚拟化下要 GVA→GPA→SPA 两阶段翻译 |
| N-Trace | RISC-V 基于 Nexus 的处理器追踪（trace）消息格式规范，1.0 是版本号；用硬件把执行路径压缩输出，供调试/性能分析 |
| IME | SpaceMiT 的矩阵乘累加指令集扩展；1.0 每核私有，2.0 双核共享 |
| VLEN / ELEN | 向量寄存器位宽 / 单个元素最大位宽 |
| LMUL | 向量寄存器分组倍数；LMUL=4 表示一条指令用 4 个向量寄存器 |
| MMA | Matrix Multiply-Accumulate，矩阵乘累加 |
| APLIC / ACLINT | AIA 的平台级中断控制器 / 核心本地中断器 |
| MSI | Message-Signaled Interrupt，设备写内存触发的中断 |
| IOMMU | I/O 内存管理单元，做 DMA 地址翻译与隔离 |
| SPP | Stream-based Page Prefetching，一种预取算法 |
| CleanUnique | 缓存一致性协议事务类型，用于高并发锁场景避免活锁 |
| Operational Intensity | 每字节内存流量能换多少次 MAC，单位 MAC/B |
| Little's Law | 稳态下 并发数 = 吞吐 × 延迟；用于主存在途窗口设计 |
| BTM | Branch Trace Message，N-Trace 的一种输出模式 |

## 12. 附录：几个容易卡住的概念

### 12.1 ISA、微架构与 Profile

**ISA（Instruction Set Architecture，指令集架构）** 是软件和硬件之间的合同：

- 有哪些指令（加、乘、load、branch、矩阵乘加……）；
- 有多少寄存器、各多宽；
- 支持哪些数据类型（int8/16/32/64、fp16/bf16/fp32……）；
- 地址怎么算、有哪些特权级（M/S/U）、异常和中断怎么进；
- 扩展怎么组合。

编译器只认 ISA，不认具体芯片。同一个 ISA 可以有完全不同的实现 —— 同样按 RISC-V 编译，
X100 是 4-wide 乱序、A100 是另一套配比，但**同一份二进制都能跑**。

| 概念 | 例子 | 说明 |
| --- | --- | --- |
| ISA | x86-64、ARMv9、RISC-V | 指令合同 |
| 微架构 | 4-wide 乱序、TAGE 分支预测、几级流水 | 这颗芯片**怎么实现** ISA |
| Profile | RVA23 | RISC-V 的「打包配置」：把一堆扩展锁成必选集合 |

RISC-V 是模块化的：基础整数指令 `RV64I` + 扩展 `M`（乘除）、`A`（原子）、`F/D`（浮点）、
`C`（压缩）、`V`（向量）、`H`（虚拟化）…… **RVA23 是一个 Profile**，规定应用处理器
至少要有哪些扩展，保证「按 RVA23 编译的程序」在任意 RVA23 机器上都能跑。

白皮书说 X100 和 A100「同一套 ISA」，意思是：同一个 Linux、同一个编译器产出的代码，
两边都能执行 —— 所以不需要两套驱动、两套运行时。**例外**是 A100 没实现 H 扩展，
不能当 hypervisor 宿主。

### 12.2 N-Trace 与处理器追踪

**处理器追踪（processor trace）**：CPU 一边跑，一边把「执行到哪、跳去哪」编码成一条
压缩消息流，从专门的 trace 口送出来；离线工具把它还原成完整执行路径。

它不会记录每条指令的完整地址（带宽吃不消），而是记 **BTM（Branch Trace Message）**：
只记分支/跳转，配合地址压缩，解码器就能重建路径。

N-Trace 1.0 是这套**消息格式规范**，基于 Nexus（IEEE-ISTO 5001 那套调试标准）。
围绕它有三个配套规范：

| 规范 | 管什么 |
| --- | --- |
| Hart-to-Trace Interface | 核**怎么把** trace 信息吐给编码器 |
| **N-Trace 1.0** | 消息**长什么样**（格式、压缩、溢出处理） |
| Trace Control Interface 1.0 | 怎么**配置**编码器（开关、触发条件） |

用途：

- **性能分析**：热点在哪、分支预测错在哪、cache 行为如何；
- **硅后调试**：系统挂死或跑飞时，看它最后执行到哪；
- **验证**：对比模拟器与真实芯片的执行路径。

普通应用开发用不到，属于 SoC 的调试/性能基础设施；用户态也没有接口去开它。

### 12.3 页表、TLB 与虚拟化的两阶段翻译

#### 三个东西

| 东西 | 在哪 | 是什么 |
| --- | --- | --- |
| **页表（page table）** | 内存里 | OS 维护的**完整映射表**：虚拟地址 → 物理地址，多级结构 |
| **TLB** | CPU 的 MMU 里 | 一张**很小的缓存**，只存最近用过的翻译结果（几十到几千项） |
| **page walk** | 硬件 | TLB 未命中时，硬件去内存里**逐级查页表**的动作 |

所以：**TLB 不是页表。** 页表是「整本电话簿」，TLB 是「手边便签，记着刚查过的几个号码」。

#### 为什么需要

程序里用的是**虚拟地址**，真正访问 DRAM 要用**物理地址**，每次访存都要翻译。
如果每次都翻整本多级页表，一次访存要额外做好几次内存访问，太慢。
于是 CPU 把最近翻译过的结果放进 TLB：

- **TLB 命中**：一两个周期拿到物理地址；
- **TLB 未命中（TLB miss）**：触发 page walk，几十到几百周期，这次访存只能等。

#### 「访问流覆盖不了 TLB」是什么意思

TLB 容量有限。如果程序在一段时间内访问的**页数**超过 TLB 能装的量，或者访问模式到处跳、
没有局部性（大数组随机访问、指针追逐、图遍历），就会频繁 miss。

这时 CPU 的时间大量花在**查地址**而不是**算数据**上，性能就塌了。
白皮书里 429.mcf（不规则访存）在虚拟化下掉 16.5%，就是这个原因。

#### 虚拟化为什么让 miss 更贵

不虚拟化时只有一次翻译：

```
虚拟地址 VA ──页表──> 物理地址 PA
```

虚拟化下是**两阶段**：

```
GVA（guest 虚拟地址）
  │  guest 的页表
  ▼
GPA（guest 物理地址，guest 以为自己拿到的「物理地址」）
  │  host 的页表
  ▼
SPA/HPA（系统物理地址 = 真实 DRAM）
```

问题在于：guest 查自己页表的**每一步**，那个页表项本身也存放在 GPA 上，
host 还得再翻译一次才能读到它。最坏情况下 5 级 × 5 级 = **25 次内存访问**
才完成一次地址翻译。

所以白皮书那句：

> TLB miss 的代价变大：访问流覆盖不了 TLB 时，每次 miss 都要多走一次 GPA→HPA 映射

翻译成人话：**guest 的 TLB 没命中时，不光要查 guest 页表，查到的每个结果还要再做一次
「guest 物理 → 真实物理」的翻译，延迟叠加。**

#### X100 怎么缓解

| 优化 | 效果 |
| --- | --- |
| L1 ITLB/DTLB 直接缓存 **GVA→SPA** | L1 命中时，虚拟化**不增加**翻译延迟（一步到位，跳过 GPA 这一层） |
| L2 TLB 同时缓存 GVA→SPA 和 GPA→SPA | 覆盖更多情况 |
| PTW 缓存非叶子页表项（GVA→GPA） | guest TLB miss 时，page walk 少走几级 |

一句话：**TLB 是地址翻译的缓存；虚拟化把一次翻译变成两次，miss 时代价翻倍；
X100 的办法是把两段翻译「拍平」后缓存在 TLB 里。**

### 12.4 IME 1.0 与 IME 2.0

**IME = SpaceMiT 的矩阵乘累加（MAC）指令扩展。** 标准 RVV 的 `V` 扩展擅长
「向量逐元素运算」，但矩阵乘（GEMM）用它要拆成很多条向量指令、来回搬数据，效率不高。
IME 相当于在 CPU 里加了**专用的矩阵运算单元**。

白皮书里是两代硬件通路：

| | IME 1.0 | IME 2.0 |
| --- | --- | --- |
| 归属 | **每个核私有** | **两个核共享**一个 |
| 执行宽度 | 256-bit（复用向量单元的低吞吐通路） | **1024 / 2048-bit 专用高吞吐通路** |
| 数据类型 | INT8×INT8→INT32 | INT4/INT8→INT32；FP16/BF16/FP8→FP32 |
| 矩阵形状 | 4×8 × 8×4 | INT4：8×32 / 32×8；INT8：8×16 / 16×8；FP16/BF16：8×8 |
| 定位 | 轻量小矩阵 MAC | 大模型 / Transformer 的主力矩阵通路 |

**「2.0」是硬件第二代，不是软件版本。** 相比 1.0，它更宽、支持更低精度、吞吐高得多，
但面积和功耗也大，所以做成**双核共享**来摊成本。

共享带来一个后果：**两个核必须一起喂它才能跑满**。白皮书 §5.2 那段 operational
intensity 推导就是在算这个：

- 单核、不做分块：利用率 **50%**；
- 单核、分块 + 寄存器 blocking：**66.7%**；
- 双核一起提交 MMA：共享 MAC 才能到 **100%**。

这也解释了为什么软件栈以「4 个 A100 线程一个 cluster」为调度单位，而不是单核。

**和本仓库实测的关系**：MNN 的 `-DMNN_RVV_SPACEMIT_IME2=ON` 就是让编译器生成
IME 2.0 指令；不开的话只有标准 RVV 路径，甚至会静默回退标量 —— 这就是板上
`pp512 226 tok/s` 和 `5.6 tok/s` 的差距来源。详见
[`k3-mnn-rvv/`](k3-mnn-rvv/)。
