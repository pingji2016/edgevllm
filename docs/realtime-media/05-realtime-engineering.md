# 实时工程：延迟、分块与那声「咔」

[01](01-face-filters.md) 和 [04](04-voice-neural.md) 都指向同一句话：**模型只是一部分**。
这一节讲剩下的部分，而且全都用本机数据说话。

## 一、先立预算

实时语音的延迟参考 **ITU-T G.114**（单向）：

| 单向延迟 | 体验 |
| --- | --- |
| < 150 ms | 自然，几乎无感 |
| 150–400 ms | 可接受，但能察觉 |
| > 400 ms | 像打卫星电话，说话开始相互打断 |

预算怎么分（一条变声链路）：

```
采集缓冲  5~20 ms
攒块      块长（决定性的那项）
模型推理  < 块长，否则积压
块间拼接  0（流式）~ 一个块长（块式）
播放缓冲  5~20 ms
```

**把 500 ms 的块扔进来，前面所有优化都是白费。** 所以「块长」是第一个要压的参数。

## 二、分块处理：代价与伪影

流式处理必须分块（`chunk`），而每块单独处理再拼起来会有伪影。本机实测，
用一个真实的**相位声码器**变调 1.3×，100 ms 块，9.47 s 中文语音
（[realtime_chunking.py](scripts/realtime_chunking.py)）：

| 实现 | 接缝跳变峰值 | 接缝均值 | 超标的接缝 | 每块开头/中段音量 |
| --- | --- | --- | --- | --- |
| 朴素硬拼（无上下文、不对齐） | 0.12× | 0.01× | 0/94 | 中段为 0（**空洞**） |
| + 上下文缓冲 | 5.31× | 0.69× | **19/94** | 0.75 |
| + 脉冲标定对齐 | 8.37× | 0.71× | **24/94** | 1.05 |
| + 块间交叉淡入 | **2.02×** | **0.24×** | 6/105 | 0.93 |

标尺是「这段音频自身最陡的过渡」（原始音频 `|diff|` 的 99.9 分位 = 0.197）。
比值 > 1 表示接缝处出现了音频本身不该有的东西。

听感对照（各截取前 5 秒）：

- [chunk-naive.mp3](audio/chunk-naive.mp3) —— 每 100 ms 断 50 ms 的「哒哒」
- [chunk-crossfade.mp3](audio/chunk-crossfade.mp3) —— 同上，加了上下文/对齐/交叉淡入

### 三种伪影，成因完全不同

这张表最反直觉的是**朴素实现的跳变指标最干净**（0.12×，0/94 超标）。原因不是它好，
而是它的故障模式根本不在「跳变」这个维度上：

**① 朴素实现：不是「咔」，是「缺」。**
相位声码器的首尾各要吃掉约一个窗长（1024 样本）。100 ms = 1600 样本的块喂进去，
只有约 770 个样本有重建结果，剩下填零 —— 每 100 ms 有 50 ms 是静音。
补零把每块的头尾都「洗平」了，所以跳变指标反而干净。
**只看跳变指标会完全漏掉这个 bug。** 这是实时音频里最常见的一类错误：
**没有做延迟/长度对账**。

**② 加上下文：波形完整了，「咔」才出现。**
每块两侧各多喂一个窗长的上下文，重建完整 —— 但每块的相位是**各自复位**的，
拼接点上两边的相位对不上，于是出现音频本身不该有的跳变（峰值 5~8 倍，
94 个接缝里 19~24 个超标）。**这才是那声「咔」。**

**③ 对齐 + 交叉淡入：把接缝变成可预测的、可平滑的。**
相位声码器对输入有固定的时移，用**脉冲标定**出这个值（本机实测 **−116 样本 /
−7.2 ms**，且在 4096/8192/16384 三种长度下稳定在 −114 ~ −118），裁剪时补回去，
接缝位置就固定了；再叠 10 ms 的余弦交叉淡入，残余被压到音频自身之下
（峰值 2.02×，均值 0.24×）。

> 这就是 RVC / VCClient 里 `extra_time`、上下文长度、SOLA 窗口这些参数在做的事。
> 名字不同，干的是同一件：**别让块边界上的相位和长度对不上账。**

## 三、块长 ↔ 延迟 / CPU

同一段 9.47 s 音频，不同块长下跑一遍：

| 块长 | 端到端延迟 | RTF（计算耗时/音频时长） |
| --- | --- | --- |
| 20 ms | 84.0 ms | 0.044 |
| 50 ms | 114.0 ms | 0.021 |
| 100 ms | 164.0 ms | 0.013 |
| 250 ms | 314.0 ms | 0.009 |
| 500 ms | 564.0 ms | 0.008 |

（延迟 = 块长 + 窗长前视 1024/16000 = 64 ms；RTF < 1 表示比实时快。）

**两件事同时成立**：块越小延迟越低，但 RTF 越高。因为每块都有一份摊不薄的固定开销
（FFT、调度、函数调用）。20 ms 块的 RTF 是 500 ms 块的 5.5 倍 ——
在 DSP 上无所谓（0.044 也远小于 1），但**换成神经网络就致命了**：
推理开销大一到两个数量级，20 ms 的块很可能直接 RTF > 1，开始积压。

> **选块长的实际做法**：先把模型的单次推理时间测出来（P99，不是均值），
> 块长取它的 2~3 倍，然后看这个块长带来的延迟能不能接受。不能接受就得换更小的模型，
> 而不是继续压块长。

## 四、音频回调里的三条铁律

实时音频线程（callback）跑在硬实时上下文里，**任何一次阻塞都是爆音**：

1. **不分配内存。** `malloc`/`new`/容器扩容都可能触发锁或页错误。
   所有缓冲在初始化时预分配好。
2. **不拿锁、不打印、不写文件。** 日志和磁盘 I/O 是延迟尖峰的主要来源。
   要输出信息，写进无锁队列，让别的线程去落盘。
3. **用无锁的单生产者单消费者（SPSC）环形缓冲**跨线程传数据。

```c
// SPSC 环形缓冲的核心：只有两个原子索引，读写各自推进，不互相等
// 生产者（音频回调）只写 write_idx，消费者只写 read_idx
size_t n = (write_idx - read_idx);          // 已填充
if (n + len > capacity) { /* 溢出：丢弃或做漂移补偿 */ }
```

两个必须处理的现实问题：

- **溢满/欠载**：采集和播放的时钟不是同一个晶振，长时间必然漂移。
  要么丢/补样本，要么做**重采样漂移补偿**（推荐，听不出来）。
- **线程优先级**：把音频线程提到实时优先级，否则一个后台编译就能让它爆音。

## 五、ONNX Runtime 上跑哪块硬件

神经变声器导出 ONNX 后，后端选择直接决定能跑到多快：

| Execution Provider | 平台 | 备注 |
| --- | --- | --- |
| `CPUExecutionProvider` | 全平台 | 兜底；小模型（Beatrice 2 级）够用 |
| `CUDAExecutionProvider` | NVIDIA | 本机（RTX 5060 Ti）走这条；**sm_120 需要 CUDA 12.8+** |
| `TensorRTExecutionProvider` | NVIDIA | 更快，但首次构建引擎要几分钟，**不适合每次启动都重建** |
| `DmlExecutionProvider` | Windows 任意 GPU | DirectML，不装 CUDA 也能用独显 |
| `OpenVINOExecutionProvider` | Intel CPU/iGPU/NPU | 酷睿核显/ NPU 场景 |
| `CoreMLExecutionProvider` | Apple | ANE/GPU |
| `NNAPI` / `QNN` | Android / 高通 | 手机的 NPU |

选型经验：

- **Windows + NVIDIA，只想少装东西** → DirectML；**要最低延迟** → CUDA。
- **TensorRT 的引擎构建时间**在实时变声里通常不值得（除非能缓存引擎文件）。
- **手机上别指望 CUDA**，走 NNAPI/QNN，把模型量化到 int8。

## 六、把两张表放一起看

| 环节 | 人脸 | 变声 |
| --- | --- | --- |
| 模型本身 | 检测 10.3 ms，不贵 | 变声网络 919 ms（CPU），很贵 |
| 真正的开销 | **逐像素变形 97.6 ms** → ROI 后 7.4 ms | **块长** + 每块固定开销 |
| 优化第一刀 | 限制 ROI / 上 GPU shader | 压块长 + 对账延迟 |
| 优化第二刀 | 拆分「检测频率 ≠ 变形频率」 | 无锁缓冲 + ASIO 驱动 |
| 共同结论 | **模型很快，周边很慢** | 同左 |

## 小结

1. **延迟预算是设计起点**（G.114：单向 < 150 ms 自然）。先立预算，再选模型。
2. **分块必须有上下文 + 对齐 + 淡入**，缺一样就是「咔」或「缺」。
   而且**跳变指标会漏掉「缺」** —— 要同时看电平。
3. **块长既决定延迟也决定 CPU 占用**，两者反向。实际做法是先测模型推理 P99，
   再取 2~3 倍当块长。
4. **音频回调里不分配、不加锁、不打印**，跨线程用 SPSC 环形缓冲，并处理时钟漂移。
5. **ONNX EP 是免费的加速**：同一份模型换一个 Provider，延迟可能差一个数量级。
