# 神经变声：RVC 一族在做什么

[03](03-voice-pitch-and-formant.md) 里的 DSP 方法解决的是「音高多少」，解决不了
「听起来像谁」。想从男声变成另一个人的女声，光搬音高不够 —— 得**换掉音色本身**。
这就是神经变声（Voice Conversion, VC）要干的事。

## 一、RVC 的流水线

RVC（Retrieval-based Voice Conversion）是这一族里生态最好、最常被抄的一个。
它的管线是：

```
输入音频（任意采样率）
   │
   ├─▶ 重采样到 16 kHz ─▶ HuBERT / ContentVec ─▶ 内容特征（768 维，每 ~20 ms 一帧）
   │                                              │
   │                                ┌─────────────┴──────────────┐
   │                                ▼                            ▼
   │                     FAISS 索引检索（Top-1）            与原始特征混合
   │                     （目标说话人的特征库）              （index_rate 控制）
   │                                │
   ├─▶ RMVPE ─▶ F0 曲线 ────────────┤
   │                                ▼
   └──────────────────────▶ VITS（encoder + flow + decoder）─▶ 梅尔谱
                                    │
                                    ▼
                              HiFi-GAN 声码器 ─▶ 波形
```

四个关键设计，每个都可以单独拎出来讲：

### 1. 内容与音色解耦：ContentVec

HuBERT 是自监督语音模型，它的中间表示主要编码**说了什么**（音素内容），
对**谁说的**相对不敏感。ContentVec 是它的改进版，进一步抹掉说话人信息。
所以拿它当「内容编码器」，音色就是后面注入的。

### 2. F0 单独抽：RMVPE

音高不交给神经网络隐式学，而是用一个专门的 F0 估计器抽出来，**当显式条件**喂进去。
好处是可以**直接改**：

- `f0_up_key` 调高/调低 → 变调
- **不喂 F0** → 音高也一起换（适合男→女这种大跨度）
- 喂 F0 → 保留原音高，只换音色（适合同性别、保留语调）

这一步就是 [03](03-voice-pitch-and-formant.md) 里「音高是一个量」的工程落地：
神经变声器之所以能同时做到「像另一个人」和「音高我说了算」，就是因为 F0 是显式输入。

> F0 估计器选型：RMVPE（当前主流，快且准）、CREPE（准但慢）、
> Harvest/DIO（WORLD 家的，传统但稳）。RVC 的默认从 harvest 换到 RMVPE 是明显的音质升级。

### 3. 特征检索：FAISS Top-1

这是 RVC 名字里那个 **R**（Retrieval）。训练时会存下目标说话人所有帧的内容特征，
建成一个 FAISS 索引。推理时，每一帧拿输入特征去查**最像的那一帧目标特征**，
用它（按 `index_rate` 与原特征混合）当作解码输入。

它解决的是「小数据训出来的模型发音含糊」：检索相当于从目标说话人的真实录音里
「就近取材」，把细节找回来。代价是训练时会多一个索引文件，推理时多一次向量查询
（很快，但索引是内存里的）。

### 4. VITS + HiFi-GAN

VITS 是端到端的 TTS 结构（encoder + 归一化流 + 解码器），输出梅尔谱；
HiFi-GAN 是声码器，把梅尔谱变成波形。RVC 复用了这一整套，只把条件换成了
「内容特征 + F0 + 检索特征」。

### 训练成本

RVC 的门槛低得离谱：**10 分钟左右的干净语音**，单卡几十分钟到几小时就能出一个可用的
模型。这就是它能在社区里爆发的直接原因 —— 也是它引发大量伦理问题的直接原因。

## 二、同类项目横评

| 项目 | 定位 | 需要训练吗 | 特点 |
| --- | --- | --- | --- |
| **RVC** | 变声（VC） | 需要，~10 min 数据 | 生态最大，音质/速度平衡好，ONNX 导出成熟，实时方案最多 |
| **so-vits-svc** | 变声（VC） | 需要 | 音质好，配置比 RVC 更繁琐，社区模型多 |
| **DDSP-SVC** | 变声（VC） | 需要 | 轻、训练快，音质略弱，适合显卡差的人 |
| **seed-vc** | **零样本**变声 | **不需要** | 几秒参考音频就能换，GPL-3.0；项目自述「准实时」（~430 ms 量级） |
| **GPT-SoVITS** | TTS + 声音克隆 | 少样本（~1 min） | 更偏「说话」而不是「换声」，中文场景很流行 |
| **kNN-VC** | 零样本变声 | 不需要 | 学术方案：直接在自监督特征空间做最近邻替换，思路干净 |

**两条路线**：

- **训练型**（RVC 一族）：音质上限高、稳定，但要为每个目标声音训一次。
- **零样本**（seed-vc / kNN-VC）：拿来即用，音质和稳定性略逊，适合尝鲜和长尾声音。

## 三、实时化：延迟从哪来

实时变声的延迟预算（单向）业内参考 **ITU-T G.114**：< 150 ms 感觉自然，
150–400 ms 可接受，超过 400 ms 像在打卫星电话。拆开看：

```
采集 → 攒够一个块 → [重采样|F0|特征|解码|声码器] → 块间拼接 → 播放 → 输出缓冲
  ↑          ↑                    ↑                   ↑          ↑
 设备缓冲   块长（大头）      模型推理时间          SOLA/淡入    设备缓冲
```

- **块长是大头**。500 ms 的块，光攒数据就 500 ms，后面所有优化都没意义。
  这也是为什么所有实时变声器都在往 20–100 ms 的块长挤。
- **模型推理必须比块长短**，否则会持续积压（RTF > 1 就是不可实时）。
- **块间拼接**如果不做处理，每块边界都是一声「咔」——
  这在 [05-realtime-engineering.md](05-realtime-engineering.md) 里有实测。

### 已有方案的实测数字

| 方案 | 延迟（项目自述，配置相关） | 说明 |
| --- | --- | --- |
| **Beatrice 2** | ~50 ms | 无 GPU 也能跑，极轻量，代价是音色表现力有限 |
| **VCClient (w-okada)** 默认 | ~170 ms | **客户端-服务端分离**：客户端只做音频 I/O，服务端做推理，走 WebSocket |
| **VCClient + ASIO** | ~90 ms | 换掉 WASAPI 走 ASIO 驱动，省掉系统音频栈的缓冲 |
| **seed-vc** | ~430 ms | 零样本的代价；项目自己描述为「准实时」 |

**客户端-服务端分离**是 VCClient 最值得抄的设计：推理端可以是另一台带显卡的机器，
采集端可以是手机/树莓派。延迟只多一个网络 RTT（局域网 1 ms 级），
换来的是「采集设备可以没有算力，算力设备可以不接声卡」。RVC 的实时 fork
大多沿用这个结构。

### 音频设备链路（Windows 上的实际接法）

想让变声后的声音进到游戏/会议软件里，需要一个**虚拟声卡**做路由：

```
麦克风 → [变声器] → VB-Cable / VoiceMeeter（虚拟输出）→ 游戏/会议软件选它当输入
```

| 平台 | 低延迟驱动 | 虚拟声卡 |
| --- | --- | --- |
| Windows | **ASIO**（绕过系统混音器，最低延迟）→ 其次 WASAPI | VB-Cable、VoiceMeeter、Virtual Audio Cable |
| macOS | CoreAudio | BlackHole（开源、免费） |
| Linux | JACK / PipeWire | PipeWire 的 loopback 模块 |

**ASIO 值不值得**：从上面的表看，170 ms → 90 ms 的差距主要来自这一个驱动，
对唱歌/对唱类应用是能感觉出来的差别。普通聊天 170 ms 完全能用。

## 四、本机视角：CPU 还是 GPU

本目录的所有 DSP 实验都在 CPU 上跑（见 [scripts/README.md](scripts/README.md)），
DSP 变声 CPU 绰绰有余。神经变声的情况完全不同：

| | CPU | GPU |
| --- | --- | --- |
| Beatrice 2 这类极轻模型 | 可以（~50 ms） | 更快，但没必要 |
| RVC | 通常不行（推理超块长 → 积压） | 推荐 |
| 大模型 / 零样本 | 不行 | 必须 |

如果只有 CPU，实用组合是：**Beatrice 2 或世界模型/DSP 方案**，
而不是硬上 RVC。

导出成 **ONNX** 是让神经网络跑到任意设备（含手机/NPU）的通用做法，
ONNX Runtime 的 Execution Provider 选择见
[05-realtime-engineering.md](05-realtime-engineering.md)。

## 五、许可与伦理（比人脸那边更敏感）

- **仓库是 MIT，权重不是。** RVC 代码 MIT，但社区流通的预训练权重**大量**基于
  动漫/游戏/虚拟歌手的语音训练，这些数据集和模型本身的权利状态是灰色的。
- **seed-vc 是 GPL-3.0**，商用集成要注意传染性。
- **声音权和肖像权一样是法定权利。** 中国《民法典》第 1023 条把自然人声音的
  保护**参照肖像权**；未经许可克隆他人声音用于发布/诈骗，在几乎所有司法辖区都违法。
  近期已有多起「AI 配音侵权」判例。
- 本目录不做任何真人声音的克隆，语音素材全部来自系统 TTS。

## 小结

1. **神经变声 = 内容/音色解耦 + 显式 F0 + 声码器**。RVC 用 ContentVec 解耦、
   用 FAISS 检索补细节、用 VITS+HiFi-GAN 出声。
2. **F0 是显式输入**，所以「换音色」和「改音高」可以独立控制 ——
   这是 [03](03-voice-pitch-and-formant.md) 那条原理在网络时代的落地。
3. **要不要训练是选型的第一问**：RVC 一族要训（10 分钟数据），seed-vc 一类零样本不用。
4. **延迟的第一来源是块长，第二是驱动**。ASIO 能省掉近一半，虚拟声卡负责路由。
5. 剩下的全是实时工程问题 —— 下一节 [05-realtime-engineering.md](05-realtime-engineering.md)。
